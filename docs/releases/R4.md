# R4 — Sprints 5–6: "Money is safe under every failure; chaos proven in CI; security foundations"

Version 1.0 · 2026-09-23 · Sprints 5–6 (E4 — Resilience, plus E5 — Security's first half), per `docs/07-delivery-plan.md` §2–3

Sprint goal achieved: a purchase that times out, gets reversed by the issuer, or answers late no longer risks the cardholder's money or the ledger's correctness. Every failure path — timeout, reversal, duplicate, late response — now resolves deterministically instead of silently. A learner can switch on six real network failures from the console and watch the system protect money in real time, and that ledger-invariant guarantee is now proven automatically in CI, not just by hand. On top of that, the gateway and issuer now protect PINs and message integrity for real: PIN blocks are translated under HSM-simulated keys and never appear in the clear outside one function call, every message is MAC-verified, and a PCI scanner + gitleaks run on every PR to catch card-data or secret leaks before they reach `main`.

**Status: final.** This release originally shipped as a Sprint-5-only draft (see the addendum note below) because `docs/07-delivery-plan.md` §3's sprint table stamps the `R4` release marker on Sprint 6, not Sprint 5 — Sprint 6 adds `MCN-407` (the automated chaos test suite), `MCN-501` (security module/key store, split ISS+GW), `MCN-502`/`MCN-503` (PIN translation/MAC, both sides), and `MCN-506` (PCI scanner in CI). All of that has now landed, matching exactly how `R3` shipped across Sprints 3–4: the feature-slice work finished one sprint before the release's own automated proof and security foundation did. This file now covers all twelve stories across both sprints as the complete R4.

Required as a standalone contracts-only PR ahead of MCN-502's own code per `CLAUDE.md` §9. |
| MCN-502 | [#55](https://github.com/pcaokhai/mini-card-network/pull/55) | GW | PIN translation and MAC (gateway): `hsm.Module` gains `TranslatePIN` (TPK→ZPK, clear PIN block exists only inside one function call) and `ComputeMAC`; `purchase.Service.sendPurchase` MACs every outgoing 0200 into DE 64/128 and verifies every incoming 0210's MAC — a mismatch sets RC 96, queues a reversal through MCN-401's existing `ReversalQueuer`, and increments `mcn_mac_failure_total`. |
| MCN-503 | [#56](https://github.com/pcaokhai/mini-card-network/pull/56) | ISS | PIN and MAC verification (issuer): `VerifySecurity` (previously a no-op) now verifies the MAC first — a bad MAC sets RC 96 and aborts before any PIN check, so `pin_try_count` never moves on an unverified request — then decrypts DE 52 under ZPK and checks a simulated PVV against `card.pvv`; wrong PIN sets RC 55 and increments `pin_try_count`, the third consecutive miss sets `card.status = PIN_BLOCKED` and RC 75. ## How to test

### 1. Reversal and SAF durability (gateway + issuer, real stack)

```bash
make up
cd gateway-go && go test ./internal/saf/... ./internal/purchase/... -v
```

The `kill -9`-during-load durability test (MCN-401-AC4) is the one worth reading directly: it kills the SAF worker mid-delivery and asserts every pending reversal still gets delivered after restart — not just that the process comes back up.

### 2. Ledger correctness under any interleaving (issuer)

```bash
cd issuer-jpos && ./gradlew spotlessCheck build
```

The property-style interleaving test for MCN-402-AC4 runs many seeded-random orderings of original/duplicate/reversal/repeat and asserts the ledger's Σ stays balanced after every one — a real invariant proof, not a handful of hand-picked cases.

### 3. Chaos scenarios end to end (real stack)

```bash
make up
curl -s -X POST localhost:8080/v1/chaos/scenarios/timeout_3s -d '{"enabled":true}'
curl -s -X POST localhost:8080/v1/chaos/runs -d '{"count":50}' | python3 -m json.tool
```

Expect `closingBalanceTotal` to reconcile against `openingBalanceTotal − approved + reversed` with zero discrepancy. `drop_response` now routes through the real MCN-407 fake-issuer simulator instead of returning a `501`.

### 4. Chaos Lab and failure journeys (web console, mock mode)

```bash
cd web-next && NEXT_PUBLIC_API_MOCKS=true pnpm dev
```

- `/lab/chaos` — toggle each of the six scenario cards, start a run, watch the money-verification panel update live and flash on completion.
- `/transactions/{rrn}` — open a reversed/timed-out transaction fixture and watch the countdown ring during autoplay; confirm the money panel shows the debit-then-refund pair.

### 5. Integration checkpoint (real issuer + real gateway)

```bash
make up
cd web-next && NEXT_PUBLIC_API_MOCKS=false pnpm dev
```

Run a purchase against a card configured to time out (or toggle a chaos scenario first), confirm the POS shows RC 68, open the transaction's journey and see the REVERSAL/WARN steps render for real, then open Chaos Lab and run a synthetic batch to see a real zero-discrepancy result.

### 6. Automated chaos proof in CI (Sprint 6)

```bash
make chaos
```

Runs the six chaos scenarios at dev scale, asserts zero ledger discrepancy, no DEAD SAF items, and no non-final transactions after drain, then writes a markdown report. CI runs 500 tx/scenario on any PR labelled `chaos` and 10,000 nightly.

### 7. PIN protection and message integrity (Sprint 6)

```bash
cd gateway-go && go test ./internal/hsm/... ./internal/purchase/... -run MAC -v
cd issuer-jpos && ./gradlew test --tests VerifySecurityTest
```

`VerifySecurityTest` and the gateway's MAC golden-vector test (`TestJCEModule_computeMAC_matchesGoldenVector`) both verify against the same `contracts/iso8583/vectors/mac/*.json` fixtures — proof both sides compute an identical MAC, not just independently "probably compatible" ones. To see a real PIN-block reject: send three purchases with a deliberately wrong PIN against the same card and confirm the third response is RC 75 with `card.status = PIN_BLOCKED` in the issuer's DB.

### 8. PCI and secret scanning (Sprint 6)

```bash
make pci-scan
```

Scans fixtures, logs and a DB dump for Luhn-valid PANs, PIN block and track patterns (skipping the allow-listed simulator fixture); `gitleaks` runs alongside it in CI on every PR. `.gitleaks.toml` at the repo root allowlists one known-safe synthetic test fixture (a base64 AES key that decodes to sequential digits) — see Known gaps for why that entry exists.

### 9. Per-lane commands (also run in CI, per changed path)

```bash
make -C issuer-jpos test        # ReversalHandlingIntegrationTest, VerifySecurityTest, ledger-interleaving property test, etc.
make -C gateway-go lint test    # go vet, golangci-lint, go test -race — internal/saf, internal/purchase, internal/chaos, internal/hsm
make -C web-next lint test      # eslint, tsc, vitest — chaos-client, ScenarioCard, MoneyVerificationPanel, JourneyScreen
make contracts                  # includes the new contracts/iso8583/vectors/mac/*.json vectors, still green
```

## Resolved during Sprint 6 (tracked as gaps in the earlier draft of this release)

- **`DROP_RESPONSE` chaos scenario** now has a real fake-issuer simulator (MCN-407) instead of a `501` stub.
- **`MCN-407`'s automated 10,000-tx/scenario ledger-invariant proof** is now real and wired into CI (`chaos` job, PR-label-gated at 500 tx/scenario, nightly at 10,000).
- **Key material, PIN blocks and message integrity** went from nonexistent to real (MCN-501/502/503): no clear key ever stored, PIN blocks translated and discarded within one function call, every message MAC-verified end to end.

## Known gaps (residual, not blocking)

- **The chaos run's money verification (`closingBalanceTotal`) is still an internal-consistency check against the run's own approved/reversed tallies, not a live cross-check against the issuer's real ledger** — no gateway-owned ledger-balance API exists yet. A real cross-check needs a future issuer balance-query story; flagged with a `ponytail:` comment in `gateway-go/internal/chaos/runner.go`. Not resolved by Sprint 6.
- **`issuer-jpos`'s Docker build fails in some local environments**: `generatePackager` can't see `/contracts/iso8583/packager-spec.yaml` because the Docker build context is `./issuer-jpos` only, not the repo root — found while landing MCN-407, which needed a real stack to verify the fake-issuer simulator against. GitHub Actions' `lint-test-iss` job builds via `gradlew` directly and isn't affected, but `make up` with `issuer-jpos` included will hit this locally until the build context is fixed. Tracked, not fixed this release.
- **A synthetic base64 AES-key test fixture in `gateway-go/internal/config/config_test.go` is allowlisted in `.gitleaks.toml`** rather than fixed at the source, because gitleaks scans historical commit diffs, not current file content — an earlier attempt at an inline `//gitleaks:allow` comment silently didn't suppress the finding since the offending commit predated the comment. The identical fixture value also still exists unguarded in other already-merged commits from before gitleaks was wired in (Sprint 5 and earlier) — it won't be flagged again unless something else touches those files, since gitleaks in this CI setup only scans each PR's own diff, not the full repository history. Worth a one-time full-history scan someday; not blocking.
- **Sprint 5's real CI failures, fixed directly during landing rather than deferred**: `golangci-lint`'s `gocyclo` check flagged `cmd/gateway.run` and `purchase.Service.sendPurchase` over the complexity-10 threshold from MCN-404's chaos wiring (fixed by extracting closures into named functions) — the same `gocyclo` regression on `cmd/gateway.run` recurred **twice more** in Sprint 6 as MCN-501's `hsm`/key-store wiring and MCN-407's fake-issuer wiring each independently pushed it back over 10; each time fixed the same way. A `TestRun_stopsCleanlyOnCancel__MCN_005_AC4` failure (Testcontainers Postgres connection reset under `-race`) was confirmed a pure flake by re-running the identical commit clean.
- **Every merge across both sprints but the very first hit the "checks show green but the branch is behind `main`" gotcha** first documented in the Sprint 3–4 lessons — worst case in Sprint 6, where `MCN-501-GW` needed three separate rebases as MCN-407, MCN-501-ISS and MCN-506 each landed underneath it in turn, hitting a real additive struct-field merge conflict along the way. Worth continuing to check `git merge-base --is-ancestor origin/main HEAD` before every merge, not just when a merge is outright rejected — `gh-axi run list` also showed stale/incomplete data more than once this sprint; cross-checking with `gh api ".../actions/runs?head_sha=<sha>"` directly caught it.
