# R4 — Sprint 5: "Money is safe under every failure"

Version 1.0-draft · 2026-09-23 · Sprint 5 (E4 — Resilience), per `docs/07-delivery-plan.md` §2–3

Sprint goal achieved: a purchase that times out, gets reversed by the issuer, or answers late no longer risks the cardholder's money or the ledger's correctness. Every failure path — timeout, reversal, duplicate, late response — now resolves deterministically instead of silently. A learner can also switch on six real network failures from the console and watch the system protect money in real time.

**Status: DRAFT, early.** Both feature slices this release is tagged to in `docs/07-delivery-plan.md` §2 (S4a, S4b) are fully shipped as of this draft — every story below is merged to `main`. But `docs/07-delivery-plan.md` §3's sprint table stamps the `R4` release marker on **Sprint 6**, not Sprint 5, because Sprint 6 adds `MCN-407` (the automated chaos test suite that proves the ledger invariant holds under 10,000 transactions per scenario in CI) plus `MCN-501`/`MCN-506` (key rotation, PCI scanner) in the same release. This mirrors exactly how `R3` shipped across Sprints 3–4: the feature-slice work finished one sprint before the release's own automated proof did. Treat this file as the Sprint 5 half of R4 — a `docs/releases/R4-addendum.md` (or an edit here) should follow once MCN-407/501/506 land in Sprint 6, the same way `docs/plans/SPRINT-4.md` flagged R3 in advance.

## How to test

### 1. Reversal and SAF durability (gateway + issuer, real stack)

```bash
make up
cd gateway-go && go test ./internal/saf/... ./internal/purchase/... -v
```

The `kill -9`-during-load durability test (MCN-401-AC4) is the one worth reading directly: it kills the SAF worker mid-delivery and asserts every pending reversal still gets delivered after restart — not just that the process comes back up.

### 2. Ledger correctness under any interleaving (issuer)

```bash
cd issuer-jpos && ./gradlew spotlessCheck build
```

The property-style interleaving test for MCN-402-AC4 runs many seeded-random orderings of original/duplicate/reversal/repeat and asserts the ledger's Σ stays balanced after every one — a real invariant proof, not a handful of hand-picked cases.

### 3. Chaos scenarios end to end (real stack)

```bash
make up
curl -s -X POST localhost:8080/v1/chaos/scenarios/timeout_3s -d '{"enabled":true}'
curl -s -X POST localhost:8080/v1/chaos/runs -d '{"count":50}' | python3 -m json.tool
```

Expect `closingBalanceTotal` to reconcile against `openingBalanceTotal − approved + reversed` with zero discrepancy. Toggle `drop_response` and expect a `501` (no fake-issuer simulator yet — see Known gaps below).

### 4. Chaos Lab and failure journeys (web console, mock mode)

```bash
cd web-next && NEXT_PUBLIC_API_MOCKS=true pnpm dev
```

- `/lab/chaos` — toggle each of the six scenario cards, start a run, watch the money-verification panel update live and flash on completion.
- `/transactions/{rrn}` — open a reversed/timed-out transaction fixture and watch the countdown ring during autoplay; confirm the money panel shows the debit-then-refund pair.

### 5. Integration checkpoint (real issuer + real gateway)

```bash
make up
cd web-next && NEXT_PUBLIC_API_MOCKS=false pnpm dev
```

Run a purchase against a card configured to time out (or toggle a chaos scenario first), confirm the POS shows RC 68, open the transaction's journey and see the REVERSAL/WARN steps render for real, then open Chaos Lab and run a synthetic batch to see a real zero-discrepancy result.

### 6. Per-lane commands (also run in CI, per changed path)

```bash
make -C issuer-jpos test        # ReversalHandlingIntegrationTest, ledger-interleaving property test, etc.
make -C gateway-go lint test    # go vet, golangci-lint, go test -race — internal/saf, internal/purchase, internal/chaos
make -C web-next lint test      # eslint, tsc, vitest — chaos-client, ScenarioCard, MoneyVerificationPanel, JourneyScreen
make contracts                  # unaffected by this release, still green
```

## Known gaps (deliberate, tracked for Sprint 6)

- **`DROP_RESPONSE` chaos scenario has no real backing simulator yet** — MCN-404 stubs it with a proper `501`, not a silent no-op, rather than duplicating work that belongs to `MCN-407` (the fake-issuer / chaos test suite story) in Sprint 6.
- **The chaos run's money verification (`closingBalanceTotal`) is an internal-consistency check against the run's own approved/reversed tallies, not a live cross-check against the issuer's real ledger** — no gateway-owned ledger-balance API exists yet (only the issuer owns real accounts). A real cross-check needs a future issuer balance-query story; flagged with a `ponytail:` comment in `gateway-go/internal/chaos/runner.go`.
- **`MCN-407` (10,000-transactions-per-scenario automated chaos proof in CI) has not landed yet** — everything in this release has been verified by hand and by the per-story integration/property tests above, but the sprint's own automated ledger-invariant-under-chaos gate is Sprint 6 work. Treat this release's chaos guarantees as story-level proven, not yet CI-enforced at scale.
- **A real CI failure was root-caused and fixed directly during landing, not deferred**: `golangci-lint`'s `gocyclo` check flagged `cmd/gateway.run` (complexity 11) and `purchase.Service.sendPurchase` (complexity 12) — both genuinely pushed over the threshold-10 limit by MCN-404's chaos wiring, despite the story's own verification claiming zero new findings. Fixed by extracting the late-response and chaos-duplicate-hook closures into named functions and splitting `sendPurchase`'s duplicate-send and post-send finalization into their own methods; no behavior change. A separate CI run then failed on `TestRun_stopsCleanlyOnCancel__MCN_005_AC4` with a Testcontainers Postgres connection reset under `-race` — confirmed as a pure flake by re-running the identical commit, which passed clean.
- **Every merge in this sprint but the first hit the "checks show green but the branch is behind `main`" gotcha** first documented in `docs/07-delivery-plan.md`'s Sprint 3–4 lessons — MCN-402, MCN-404 (before its own lint fix), and MCN-406 all needed a rebase and re-verification before the real required-checks count was satisfied. Worth continuing to check `git merge-base --is-ancestor origin/main HEAD` before every merge, not just when a merge is outright rejected.
