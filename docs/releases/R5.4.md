# R5.4: fixing every gap the per-page API contracts found, in priority order

Version 1.0 · 2026-09-26 · Patch release on R5.3 (per-page API contract docs), fixing the gaps those docs recorded, plus ADR-007

**Why:** after `docs/api/*.md` (R5.3's contract docs) recorded every gap between contract, spec and real behaviour across all nine console pages, the user asked to fix all of them, in priority order, then document the fix in detail. The agreed order was PCI leaks first (LAB-G1/G2), then money-safety (POS-G4, POS-G14, CHA-G1 and the rest of the reversal/ledger chain), then everything else — scoped to stories at or before Sprint 8 (root CLAUDE.md's story table). Sprint 9+ work (MCN-802 switch/STIP, MCN-702/704 settlement backend) and unbuilt stories (MCN-601 holds/completion) were explicitly excluded, not silently skipped.

**Status: final.** 17 PRs are squash-merged to `main` with green CI. Every PCI and money-safety finding is fixed; every should-fix a security review raised is either fixed or recorded as an open, low-priority gap row with its own id. Four PRs went through an independent security review before merge, because they touched PAN/key/money-path code (root CLAUDE.md §4 step 7); three of those were sent back at least once with a real blocker, fixed, and re-reviewed before merging.

## How the work was run

Same team shape as R5.1–R5.3: several `general-purpose` subagents in disjoint worktrees, one per lane (GW, ISS, WEB), plus a standing `review-pci-112` agent for independent security review. The orchestrating session never trusted a subagent's own "done" — it re-ran `gh pr checks` **and** `gh run list` on every PR before merging (a lesson from Sprint 4: `gh pr checks`' summary can look green while the underlying GitHub Actions run never happened), used `scripts/land-pr.sh` for the mechanical parts of every merge, and read the actual diff of anything security-sensitive itself before or in addition to sending it for review.

Two things this pass did differently from R5.1–R5.3:
- **Order of work matched blast radius, not story order.** PCI leaks (a raw PAN in a Lab response) shipped before money bugs (a reversal that never restored a balance), which shipped before everything else, per the user's own stated priority.
- **A blocker found in review was fixed and the same PR re-reviewed**, not waved through. Four of the seventeen PRs took two or three review rounds; every blocker below is a real one a reviewer found, not a hypothetical.

## 1. PCI: no card data in the clear (#112)

**Fixed:** LAB-G1 (`fields[].raw` carried the full PAN, only `value`/`segments[]` were masked), LAB-G2 (`GET /v1/lab/messages/samples` returned the test PAN, DE 52 PIN block and DE 64 MAC in clear; the decode response also returned DE 55 unredacted), LAB-G6 (`maxLength: 8192` on `raw` wasn't enforced).

Every Message Lab response now masks card data the same way production logs do, position-based for DE 2 so a PAN of any length is caught, plus DE 55 redaction and a real body-size cap. This went through security review before merge; the review caught two real leaks (DE 55 in clear, and glued-together PANs from a masking edge case) that were fixed before merge.

## 2. Money safety

### 2.1 Unknown outcome ⇒ reversal, everywhere (#114)

**Fixed:** JRN-G1 (journeys of pre-auth, completion, refund and balance inquiry showed "declined before reaching the issuer" although they were sent and answered), POS-G4 (advanced transactions broke root CLAUDE.md §6.4's rule — every send failure after the write now marks the row REVERSAL_PENDING and queues a 0420, never silently drops it), POS-G5 (the incoming MAC on an advanced-transaction response wasn't verified at all), POS-G9 (a timeout response claimed TIMED_OUT while the row was actually REVERSAL_PENDING).

Security review on this PR caught a double-charge path (a client disconnect mid-request could let a completion send twice) and a case where a completion advice was itself being reversed, which root CLAUDE.md §7.4 forbids (a completion repeats until 0230, it is never reversed) — both fixed before merge.

### 2.2 Refunds, reversals and card status use the real rules (#119)

**Fixed:** POS-G17 (the issuer debited the account for every processing code including refunds, so a refund took money *out* of the customer's account), POS-G19 (`LocateAndReverse` posted the reversing journal entry but never updated `account.ledger_balance`/`available_balance` — reversals never restored money), CARDS-G18 (authorization used a separate, incomplete non-active check from the one the Cards Admin API used, so a `PIN_BLOCKED` card could still transact).

**This is the bug that had already cost real money on the shared dev stack**: card `6` was found to be short exactly 807,000 ₫ (235,500 + 321,500 + 250,000), the sum of every reversal since the ledger bug shipped, because every one of them posted its reversing journal entry without ever moving the account balance to match. #119 fixes the root cause and, separately, an independent review at merge time confirmed the ledger invariant now holds under every interleaving the atomicity tests could construct.

A follow-up review nit (an abandoned-but-repeated original replayed with no response code) was fixed test-first as its own commit before merge, so a repeated 0200 of a transaction the sweeper had already abandoned correctly replays RC 94.

### 2.3 Chaos runs verify against real issuer balances (#118)

**Fixed:** CHA-G1 (the money verification was tautological — both the "closing balance" and the "discrepancy" were derived from the run's own tallies, so a run could never detect a real ledger bug), plus CHA-G2–G6, G8, G11–G13 (contract violations, no run-list endpoint, no idempotency on run start, `VERIFYING` never actually reported, chaos problem types not on the docs/04 URI scheme, no sequence number on live progress events) and LAB-G3 (encode returned no packed message).

Security review caught a run that could report a false `LEDGER_MISMATCH` after a SAF-queue drain raced the balance read, and an unhandled panic/crash mid-run leaving no result at all — both fixed before merge. The provider rules in `chaos-lab-page.md` were rewritten to describe the corrected, issuer-verified runner.

### 2.4 The transactions API: validation, idempotency, and a real race fixed under review (#117, #123, #120)

This was the largest and most reviewed chunk of the program — three PRs, four review rounds, one real money-safety blocker found and fixed.

**#117 fixed:** POS-G1–G3, G7, G8, G13 (no request validation, weak idempotency, the `Money` pattern broken for balance inquiry, missing response fields, ambiguous unknown-RRN completion behaviour), JRN-G2, G3, G6, G7 (journey builder purchase-only, detail fields never filled, unvalidated query parameters, the auto-cancelled tab conflating every reversal reason), OVW-G3, G11 (`transaction.updated` never broadcast; a declined row with no response code silently miscounted), NET-G5 (the late-response event broadcast but never persisted).

**The should-fixes, added after the first review round:** a completion that failed before sending, or that the issuer declined, left its pre-auth claimed forever with no way to complete it again — fixed by releasing the claim on any pre-send failure or genuine decline, but correctly *not* releasing it on a MAC-failure outcome, where the issuer's real decision is unknown. Separately, an idempotency key stuck in flight past its stale window with an empty RRN (proof nothing was ever sent) was still refused for a full 24 hours — fixed by letting exactly one retry reclaim it.

**The blocker, found in re-review, was real:** the reclaim mechanism itself had no fencing. A request that was merely *slow* (a database stall, not dead) could resume after its key was reclaimed by a retry, still successfully record its own RRN, and send a second live message under the same idempotency key — a genuine double-send/double-charge path. Symmetrically, the slow original's cleanup could delete the *retry's* live reservation, opening the door to a third send. **Fixed** by fencing every reservation with a per-attempt token: recording the RRN or releasing the reservation now only succeeds if the caller still holds the current token, so a reclaimed holder is refused before it can send anything, and its cleanup can't touch anyone else's reservation. The re-review verified this against tests that reproduce the actual race order, not just the happy path.

**#123 added** POS-G16: a `saf.Sweeper`, run every 30 seconds, that finds a transaction sent (or answered with an unqueued MAC-failure decline) more than 90 seconds ago with no follow-up queued, and queues the right one — a reason-68 reversal for a purchase/pre-auth/refund, a repeated completion advice for a completion, nothing for a balance inquiry. Re-review here found two more real gaps: the sweeper's own orphan query missed the MAC-failure case its own comment claimed to cover, and the guard meant to stop it double-reversing a row that had just been answered had no test proving it actually worked (the test fake always reported success). Both fixed and retested before merge.

**#120 implemented ADR-007** (OVW-G7): "today" on the Overview is now the acquirer's business date, rolling over at a configurable cutover time in `Asia/Ho_Chi_Minh`, not the UTC calendar day — so Overview no longer resets its daily counters at 07:00 local time. Because this PR could not be mechanically rebased onto the three PRs that had just landed (all of them had rewritten the same files), it was deliberately rebuilt on current `main` rather than force-merged through conflicts, and re-reviewed as a full diff rather than trusted as "just a rebase" — DE 15 (the business date field ISO 8583 requires on every message) is now correctly set from the same calendar on every code path, including the sweeper's own rebuilt messages.

## 3. Key rotation and MAC verification: four PRs, three security-review rounds, two real split-brain bugs found and fixed

This is the security-sensitive core of the program. The goal end-to-end: rotate the acquirer's ZAK/ZPK live, have both the issuer and the gateway actually use the new key immediately (not after a restart), tolerate a lost or slow reply without ever leaving the two sides on different keys, and only then remove the safety guard that disabled ZAK rotation until all of this was true.

### 3.1 Gateway-side hardening (#121)

Closed the Network and Security page gateway gaps (NET-G1–G4, G7, G9, G12–G16; SEC-G2–G6, G8, G9) and, on review, three real key-rotation bugs:
- **A lost key-change reply hung the rotation forever.** The 0800/161 send had no per-attempt deadline, so an unanswered reply meant the retry logic and the "outcome unknown, keep the key PENDING" branch could never run except on an outright connection drop — the rotation stayed RUNNING and every later rotation request got 409 until a restart. **Fixed:** each attempt now runs under its own timeout.
- **The MAC fallback could pick the wrong key**, trying only the pending key (never the retired one) and never expiring it, which could reject valid responses signed under a key an earlier rotation had already retired. **Fixed:** the fallback tries both, in order, and a successful rotation retires stale pending keys of the same type.
- **SEC-G17** (recorded, not fixed here): a resent key-change message wasn't idempotent at the issuer — fixed later, in #122.

### 3.2 Issuer reads and signs with the live key (#122, plus its own two-round review)

Fixed SEC-G15 (the issuer read `ZAK_HEX`/`ZPK_HEX` from the environment once at startup, so a rotated key was never actually used — including for the 0430's own MAC), SEC-G17 (a resent key-change message wasn't idempotent, so it could shift which key counted as "recently retired"), NET-G19 (the issuer's own 0430s were unsigned).

Two real bugs surfaced under review and were fixed before merge, both found by tests run against a real database, not by inspection alone:
- **SEC-G18, a replay bug:** nothing stopped a key-change message carrying an *already-retired* key from being replayed and re-activated. **Fixed:** any key equal to a retired row of that type is now rejected, not silently re-accepted.
- **A deeper concurrency bug the first fix didn't fully close:** two copies of the same key-change message racing each other could still let the second one's activation retire the *first* copy's row — which held the identical key — so "recently retired" became the new key all over again, the SEC-G17 bug returning through a different door. Caught in 3 of 5 real-database test runs even after the first fix. **Fixed:** an activation now never retires an already-active row holding the same key.

### 3.3 The issuer's key change wasn't atomic with its own audit log (#128, SEC-G23)

A subtler bug found only in re-review of #127 (below): the issuer committed a key's activation, then wrote its audit-log row on a separate connection afterward. If that second write failed for any reason — a database blip, a constraint — the issuer answered the key change with a decline (RC 96), even though the new key was already live. The gateway (correctly, by its own rules) reads any non-"00" reply as a real decline and retires the key it just generated — leaving the issuer signing every response with a key the gateway had just thrown away: a full outage caused by nothing more than a logging failure. **Fixed:** the audit write now happens on the same connection, inside the same transaction, as the activation itself, so a failure rolls both back together and the reply always matches what actually happened.

### 3.4 The gateway verifies the 0430's MAC, reads the ZAK live, and the rotation guard comes off (#127)

Closed NET-G20 (the gateway's SAF worker acknowledged a reversal's 0430 reply on its response code alone, never checking its MAC — a forged or corrupted 0430 could falsely complete a reversal the issuer never actually recorded) and SEC-G10 (purchase, advanced-transaction and SAF-worker code all read the ZAK once at startup, so a rotated key needed a gateway restart to take effect). With both the issuer (#122) and the gateway now reading and verifying live keys, **the SEC-G15 guard that disabled ZAK rotation entirely is removed** — `POST /v1/keys/acquirer/rotations` with `keyType: ZAK` works again.

**The blocker found here connects directly to #128 above:** before #128 merged, an issuer logging hiccup during key activation could produce exactly the false-decline outage described in §3.3. **Fixed as defence in depth, on the gateway side, independent of the issuer fix:** a key-change reply with RC 96 is now treated as an *unknown* outcome, not a decline — the gateway resends the same key up to a bounded number of attempts and only gives up with the key kept PENDING, never retiring a key on an ambiguous 96. Only an unambiguous decline, or a failure before anything was sent, still retires a key. This was landed in addition to, not instead of, #128's real fix.

**#125** (POS, Journey, Overview, Cards pages): POS-G14 (a retry after a 500/502 now reuses the same idempotency key, tied to the draft rather than the click); JRN-G5, G7, G9, G11 (live polling while a journey is unsettled, the auto-cancelled tab correctly filtered to timeout reversals only, a 404 reading as "not found" with no retry storm, an unknown step code falling back to the provider's own text); OVW-G5, G8 (decline reasons folded past the top four, a loading skeleton and error banner where the page previously showed nothing); CARDS-G3 (the BFF now sets `X-Actor` server-side on every issuer call — the browser cannot forge who acted), CARDS-G5 web half (no unblock offered for a card the issuer will refuse to unblock anyway), CARDS-G15 (two English strings translated), a real audit-timeline UI reading the issuer's own audit log instead of echoing only the current session's actions; NET-G15 (network events now map to copy by their code, not by matching English text).

## Nits recorded, not fixed — and why

Several should-fixes and nits surfaced during review were deliberately **not** fixed in this pass, each recorded as its own low-priority, open gap row so it isn't lost:

- **SEC-G19–G22** (issuer): the reversal listener's own 0430 goes out unsigned only in the narrow case where signing itself fails (key store unreachable); a PVV comparison isn't constant-time; an extracted PIN is a Java `String` and can't be zeroed from memory; a key-change decrypt failure is swallowed with no log line. None of these are exploitable today; all are cheap follow-ups.
- **SEC-G16** (residual, both PRs): a key left PENDING by a rotation with a genuinely unknown outcome has no time bound on how long it stays a MAC fallback candidate. It can't be forged (only the gateway itself generates these keys) and the next successful rotation retires it, but a key-status query would close this cleanly.
- **NET-G21** (issuer, deferred to MCN-702/Sprint 9): the issuer still takes its business date from the JVM's own clock, not from a cutover-aware calendar like the gateway's (ADR-007). Near 23:59:59, or if the issuer's container runs in UTC, the two sides can file the same transaction under different business dates — this matters for reconciliation (MCN-702), not for anything in this program.
- **SEC-G23's residual** (issuer, open): the issuer answers the same RC 96 for a genuine key-change rejection (SEC-G18's replay guard) as it does for "outcome unknown" — the gateway now treats both as unknown-outcome (§3.4), which is safe but noisier than necessary. The issuer should use a distinct decline code for an outright rejection.
