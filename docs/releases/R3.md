# R3 — Sprints 3–4: "First purchase flows work end to end on mocks and the real issuer"

Version 1.0 · 2026-09-22 · Sprints 3–4 (E3 — Authorization and POS, first half), per `docs/07-delivery-plan.md` §2–3

Sprint goal achieved: a real card purchase now clears the whole path — issuer authorization chain with a real double-entry ledger, gateway purchase flow, transaction history and journey replay, a POS simulator, an overview dashboard with a live feed, and card/account administration. This is the first release where money actually moves: a purchase against a real seeded account posts a balanced journal entry, debits the account under a row lock, and survives 200 concurrent purchases on the same card without breaking the ledger invariant.

**Why one release across two sprints, not R3 + R4:** per `docs/07-delivery-plan.md`'s feature-slice table, all three of this epic's slices (S3a purchase flow, S3b overview/journey, S3c cards) are tagged `Release: R3` — the project releases per complete feature slice, not per sprint boundary. A purchase flow (MCN-303, Sprint 3) that can't yet post a real approval (MCN-302b, Sprint 4) isn't a usable release; a POS simulator with no real money movement behind it isn't either. `docs/plans/SPRINT-3.md` said as much when it was written — its own Release line reads "— (R3 ships in Sprint 4 once MCN-302b/304/307/308/309 also land)."

## How to test

### 1. Real money movement (issuer only — the core of this release)

```bash
cd issuer-jpos && ./gradlew spotlessCheck build
```

`PurchaseDeclineIntegrationTest` and `ConcurrentPurchaseLoadTest` are the ones worth reading directly: the latter fires 200 concurrent purchases at one account and asserts the row lock serializes every debit exactly — the approval count, the final balance, and the journal-entry count all land on exact expected values, not "close enough." A real race here would show up as those numbers drifting, not a timeout.

### 2. Purchase flow (gateway, fake issuer — no Docker needed)

```bash
cd gateway-go && go test ./internal/purchase/... -v
```

Covers approval/decline mapping, RRN construction, idempotent replay, and the link-down-declines-without-sending path.

### 3. End-to-end purchase (real stack)

```bash
make up
cd gateway-go && go run ./cmd/gateway
curl -s -X POST localhost:8080/v1/transactions/purchases \
  -H 'Idempotency-Key: test-1' \
  -d '{"terminalId":"00000042","cardToken":"tok_normal","entryMode":"CHIP_PIN","amount":{"amount":10000,"currency":"704"}}' | python3 -m json.tool
```

Expect `status: "APPROVED"`, a real `authCode`, and — the same day this now became possible — the seeded `tok_normal` account's `available_balance` actually decreased by 10000 in the issuer's Postgres. Try `tok_low` (from `contracts/fixtures/cards.json`) with an amount exceeding its balance to see a real RC 51.

### 4. Transaction history and journey

```bash
curl -s "localhost:8080/v1/transactions?limit=5" | python3 -m json.tool
curl -s "localhost:8080/v1/transactions/<rrn>/journey" | python3 -m json.tool
```

### 5. Web console (mock mode, no backend needed)

```bash
cd web-next && NEXT_PUBLIC_API_MOCKS=true pnpm dev
```

- `/pos` — pick a card, enter a PIN, pay, watch the button lock during processing, see the result panel; try each of the 5 scenario buttons.
- `/` — the overview dashboard now renders for real (previously a `ComingSoon` placeholder).
- `/transactions/{rrn}` — open one from the overview feed or a POS result to see the step timeline autoplay.
- `/cards` — list cards, open one, try block/unblock and a limit change.

### 6. Integration checkpoint (real issuer + real gateway)

```bash
make up
cd web-next && NEXT_PUBLIC_API_MOCKS=false pnpm dev
```

Pay via the POS simulator, confirm a real RC 00 approval with a real auth code, open the resulting transaction's journey, open Cards and Accounts and see the real post-purchase balance change, block a card and confirm a real audit log entry.

### 7. Per-lane commands (also run in CI, per changed path)

```bash
make -C issuer-jpos test        # AccountLockRepositoryTest, LedgerRepositoryTest, ConcurrentPurchaseLoadTest, CardAdminApiIntegrationTest, etc.
make -C gateway-go lint test    # go vet, golangci-lint, go test -race
make -C web-next lint test      # eslint, tsc, vitest (unit + Storybook/a11y projects)
make contracts                  # unaffected by this release, still green
```

## Known gaps fixed while building this (worth knowing before Sprint 5)

- **The real DDL source of truth was `docs/assets/baseline-schema.sql`, not just `docs/05-data-model.md`'s prose** — MCN-201 (Sprint 2) had already built its own `acquirer_link` table before anyone found this file, with a different schema and status vocabulary than the baseline. Fixed by keeping MCN-201's shipped, live, tested schema and reconciling only the additive differences (added `name`, renamed `last_sign_on_at`→`signed_on_at`) rather than rewriting working code — documented explicitly so a future reviewer doesn't "fix" it back and break MCN-201.
- **jPOS 3.0.1 has no `PREPARED_FOR_ABORT` constant**, and — the bigger finding — **an aborted `TransactionParticipant` doesn't stop the chain, and plain participants get silently skipped on abort** unless they implement `AbortParticipant`. MCN-302a's first draft of `Respond`/`LogAndOutbox` would have never sent a response or logged a decline; fixed by implementing `AbortParticipant` on both. This same finding was reapplied in MCN-302b.
- **A real, load-bearing CI failure, twice, both root-caused rather than papered over:**
  - `ConcurrentPurchaseLoadTest`'s p99 assertion failed on GitHub Actions but not locally — turned out to be a real ~10x hardware gap (dev laptop p99≈60-110ms vs. CI's shared-runner p99≈408ms for a fully-serialized 200-request workload), not a race. Fixed by widening the connection pool to match thread count, disabling `synchronous_commit` on the ephemeral test container, and recalibrating the budget from measured CI numbers with headroom — the three ledger-invariant assertions (exact approval count, exact balance, exact journal count) were never touched and never failed.
  - `CardAdminApiIntegrationTest` failed 4/11 tests on CI with `HikariPool$PoolInitializationException` — a real connection-pool leak: each test method opened a fresh 50-connection pool in `@BeforeEach` and never closed it in `@AfterEach`, exhausting Postgres's `max_connections` after ~2 tests. Fixed by closing the pool properly.
- **CI silently not triggering at all** happened twice this release (PRs for MCN-306 and MCN-307) — a PR would show only `GitGuardian` passing with zero real GitHub Actions runs, discovered only by checking `gh run list` directly rather than trusting `gh pr checks`' summary. Both times the real cause was a stale branch that needed rebasing onto a `main` that had moved (add/add and purely-additive i18n-key conflicts in `messages/{en,vi}.json`, and once a genuine logic conflict in a new shared `money.ts` formatter both branches had independently created) — rebasing and re-pushing made CI trigger for real. Worth treating "only GitGuardian shows up" as a signal to check `gh run list`, not a green light.
- **No `internal/ws.Hub` existed before MCN-204 (Sprint 2)** and **no `useWsEvents` hook existed in `web-next` before MCN-306** — MCN-306 is the first real consumer, built against the actual merged hub envelope shape (`/v1/stream`) with no drift from what MCN-204 shipped. MCN-205's Network screen still polls; migrating it to the new hook is a flagged, deferred follow-up, not done here.
- **`response_code`/`auth_code` columns existed in `tran_log` since MCN-303 but were never persisted** — `UpdateStatus` only ever wrote `state`. Found and fixed while building MCN-304's list/journey endpoints, which depend on RC for filtering and easy-text.
- **The gateway's first keyset cursor pagination** was designed in MCN-304, since MCN-204's `/v1/network/events` (Sprint 2) shipped with only a bare `limit` and an explicit `ponytail:` comment admitting the gap. An opaque base64 `(created_at, id)` keyset was chosen over an offset specifically because an offset skips/repeats rows under concurrent inserts.
- **A subtle read-after-write bug in the Admin API's draft**: re-querying a row immediately after its own UPDATE, inside the same transaction, under READ COMMITTED isolation, doesn't reliably see the fresh values on every connection. Fixed by building the response from the known new values in memory instead of re-querying before commit.
- **PCI discipline held under real scrutiny**: MCN-305's plan draft accidentally used a real fixture card's PAN as a PIN-block test literal — caught and replaced with a synthetic non-fixture PAN before merge, since even test code must never contain a real card number from `contracts/fixtures/cards.json`.
- **Local-machine-only**: `-race` and some Testcontainers-backed tests still can't run natively on this dev Mac (broken Xcode CommandLineTools SDK for cgo-linked builds, the same documented limitation carried since Sprint 1) — proven for real on CI's Linux runners throughout.
