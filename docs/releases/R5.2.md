# R5.2: POS and Journey as in the design, and an issuer link that recovers from a sign-off

Version 1.0 · 2026-09-25 · Patch release on R5.1 (screen fidelity and fixes; no new sprint stories)

**Why:** the user sent back two screens.
- The POS screen was "not like the design".
- The Hành trình giao dịch page was empty: `/transactions` still showed "Màn hình này sẽ có ở R3".

Making both screens match the canvas (`project/POS.dc.html` and `project/Journey.dc.html`) with real data meant a contract change, gateway work and a BFF that had never been built. Verifying against the real stack then exposed a live incident: every purchase declined RC 96. Its root cause and fix are below.

**Decisions made by the user:**
- The Journey page is built to the full design (contract, gateway and web), not as a web-only restyle.
- The POS keeps all 5 transaction types (MCN-604) and drops the PIN pad, because the gateway never forwards a PIN (risk R-12).

**Status: final.** All seven PRs are squash-merged with green CI. Both screens were verified in real browser screenshots at 1440×1024 and 1280, in Easy and Expert modes, against `pnpm dev:mock` and against the real stack.

## What was fixed

Each entry covers the symptom, the root cause, the fix, and the test that guards it.

### Journey (contract, GW, WEB)

1. **`/transactions` was empty.**
   - **Cause:** the route was still the MCN-004 `ComingSoon` placeholder. The real screen lived only at `/transactions/{rrn}`, reachable from a link.
   - **Fix:** `JourneyIndexScreen` turns the canvas's scenario tabs into "the newest real transaction with this outcome": Thành công → APPROVED, Bị từ chối → DECLINED, Đã tự hủy → REVERSED.
     - The tab is URL state (`?view=`).
     - With no transaction of that kind yet, an empty state links to the POS.
   - **Test:** `JourneyIndexScreen.test.tsx`.
2. **The journey was 2–4 thin English steps with no messages.**
   - **Cause:** `journey.BuildJourney` turned each state transition into one step, and it never built an ISO message because tran_log doesn't store raw bytes.
   - **Fix (GW):** a step sequence per outcome, with actors (POS, ACQUIRER, ISSUER, SAF), offsets from the first event (never decreasing), and technical text (STAN, RC, attempts, timeout):

     | Outcome | Steps |
     | --- | --- |
     | approved | POS_REQUEST → REQUEST_SENT (0200) → ISSUER_APPROVED (0210) → POS_RESULT |
     | declined | the same, with ISSUER_DECLINED and a BAD POS_RESULT |
     | link-down | POS_REQUEST → LOCAL_DECLINE → POS_RESULT |
     | timeout | … → NO_RESPONSE → REVERSAL_QUEUED → POS_RESULT → REVERSAL_SENT (0420, or 0421 after a failed send) → REVERSAL_CONFIRMED (0430) |
     | cancellation | the approved steps, then REVERSAL_QUEUED → REVERSAL_SENT → REVERSAL_CONFIRMED |
     | any | LATE_RESPONSE at its own offset |

     - Messages are rebuilt from stored columns and follow the canvas's field sets. The 0420 fields come from the stored SAF advice (`saf.ReversalLookup` decrypts it), so DE 90 has exactly the layout that was sent.
     - DE 2 is the masked PAN only, passed through `obs.MaskPAN` again; a test feeds in a clear PAN.
     - DE 64/128 (MAC) and DE 52 (PIN block) are omitted, because they are never stored (Rulings in `docs/plans/MCN-304-journey-canvas.md`).
   - **Tests:** `internal/journey/builder_test.go`, `internal/saf/lookup_test.go`, and an api test that validates a timeout journey against `contracts/openapi.yaml`.
3. **The journey copy couldn't be translated.**
   - **Cause:** the provider sent English `title`/`easyText` strings, and the console is bilingual (vi/en).
   - **Fix:** the contract adds an optional, language-neutral `JourneyStep.code` (#92; oasdiff reports no breaking change). The web renders its own Easy/Expert copy from it, and the provider's text stays as the fallback.
     - Expert shows the provider's technical line in the timeline.
     - The detail panel keeps the Easy explanation in both modes, as the canvas does.
4. **The Journey screen didn't look like the canvas.**
   - **Fix:** the screen was rebuilt:
     - summary strip: outcome icon, headline, merchant · card · reference (RRN in Expert), total time, message count, and the customer's money;
     - "Từng bước, theo thời gian": actor chips, a pulsing current step, dimmed future steps, and Tự phát / Xem từ đầu / Bước trước / Bước tiếp;
     - "Chi tiết bước": the ISO field table (Vietnamese names in Easy, `F38` and technical names in Expert) and "Mở trong phòng lab";
     - "Tiền trong tài khoản khách";
     - the accelerated 30 s countdown on a timeout (MCN-406-AC2).
   - Autoplay uses the canvas's 950 ms per step.
   - The current step's ring is a scaled, fading pseudo-element, so motion stays on transform/opacity.
   - From 1400px up the step controls stay on the heading's row; below that they wrap. At 1280 they used to overlap the heading.
   - **Tests:** `JourneyView.test.tsx` (MCN-307-AC1/AC2, MCN-406-AC1/AC2), and `JourneyScreen.stories.tsx` (Approved, AutoReversed, Declined; axe).
5. **The money panel couldn't show "before" and "after".**
   - **Cause:** the gateway doesn't know card balances.
   - **Fix (WEB):** the card is matched by masked PAN in the Issuer Admin API. Its ledger balance is then rewound through its journals to just before this RRN's first journal.
     - The debit and credit rows are the issuer's real journals. A timed-out purchase was still debited by the issuer, which the gateway never saw.
     - A decline shows no movement.
   - **Test:** `journey-model.test.ts`.
6. **The receipt step said "the whole journey took 636 ms" on a purchase cancelled later.**
   - **Fix:** POS_RESULT is timed up to its own step.
   - **Test:** `JourneyView.test.tsx`.
7. **Seeded reversals showed their 0420/0430 about 965 s after the purchase.**
   - **Cause:** `TranLogRepository.Backdate` shifted `created_at` and the state history, but not `sent_at`, `responded_at`, `late_response_at` or the `saf_queue` timestamps.
   - **Fix:** all of them move by the same shift, in one transaction.
     - The advice's DE 7 is wire data inside the encrypted payload and isn't rewritten.
     - The journey therefore never places REVERSAL_SENT after the 0430 that acknowledged it. On live data DE 7 can also round past the ACK, since it has one-second precision.
   - **Tests:** `TestTranLogRepository_backdateMovesEveryJourneyTimestamp__MCN_002`, `TestBuildJourney_reversalSentNeverAfterItsAcknowledgement__MCN_002`.

### BFF (WEB)

8. **In real mode the browser couldn't reach the card API.**
   - **Cause:** web-next/CLAUDE.md describes Next.js as a BFF, but `src/app/api/` was never built. `.env.local` pointed the browser straight at the gateway (`NEXT_PUBLIC_API_BASE_URL=http://localhost:8080`), which answers 404 for `/v1/cards`: the Card Admin API lives on the issuer (:8081). The gateway's CORS also allowed only `http://localhost:3000`.
   - **Fix:** `src/app/api/[...path]/route.ts`.
     - `/api/v1/cards*` goes to `ISSUER_ADMIN_URL` (default `http://localhost:8081`); everything else goes to `GATEWAY_URL` (default `http://localhost:8080`).
     - Only these request headers are forwarded: Accept, Content-Type, Idempotency-Key, If-Match, traceparent. Cookies are dropped.
     - A 502 problem+json is returned when the upstream is down.
     - Real mode drops `NEXT_PUBLIC_API_BASE_URL` and uses `${origin}/api`. The local `web-next/.env.local` was updated.
   - Side effect: `If-None-Match` isn't forwarded, so the issuer's shared card ETag (see "Still open") can't serve the browser a stale 304.
   - **Test:** `src/app/api/[...path]/route.test.ts`.

### POS (WEB)

9. **The POS screen didn't look like the canvas.**
   - **Fix:** the screen was rebuilt:
     - a dark 400px terminal (merchant / TID, a green amount screen with an animated status line, a 1–9 · C · 0 · ⌫ keypad in the canvas's colours, and a 60px "Thanh toán" button);
     - coloured card tiles with each card's tag, last 4 digits and real issuer balance;
     - "Cách đọc thẻ" and "Kịch bản nhanh";
     - "Kết quả" in three states: an empty state; processing with a spinner and dots; and a result with a pop, a shake on a decline, an Expert tech line, staggered steps, and "Xem hành trình chi tiết".
   - The five transaction types are a segmented control under the heading. COMPLETION takes the original RRN, prefilled after a pre-auth, and BALANCE hides the amount.
   - **Tests:** `PosScreen.test.tsx`, `ResultPanel.test.tsx`, `pos-model.test.ts`, `CardPicker.test.tsx`, `Keypad.test.tsx`, and 10 stories with axe.
10. **The POS sent a PIN block the gateway never forwards.**
    - **Fix:** the PIN pad is removed, and the POS sends `CHIP_NO_PIN` (DE 22 `052`) or `MANUAL_NO_PIN` (`012`) with no `encryptedPinBlock`.
    - `pos-client`'s request type had made the PIN block required, which the contract does not; it now matches the contract.
    - The MCN-305-AC4 PIN tests are replaced by "sends no PIN block" (Ruling R1 in `docs/plans/MCN-305-pos-canvas.md`). `pinblock.ts` stays because the Security screen uses it.
11. **The quick scenarios included outcomes the stack can't produce.**
    - **Fix:** the pills are now outcomes the real issuer gives from `contracts/fixtures/cards.json`:

      | Scenario | Card | RC |
      | --- | --- | --- |
      | Mua hàng bình thường | 4417 | 00 |
      | Không đủ tiền | 9021 | 51 |
      | Thẻ bị khóa | 3310 | 62 |
      | Thẻ hết hạn | 7765 | 54 |
      | Vượt hạn mức | 1208 | 61 |

    - "Sai mã PIN" (R-12), "Mạng chập chờn" (needs the Chaos API) and "Quẹt từ" (no EntryMode value) are dropped.

### Link supervision incident (GW)

12. **Every purchase on the dev stack declined RC 96 while the gateway showed SIGNED_ON.**

    **Sequence**, reproduced twice:

    | Step | What happened |
    | --- | --- |
    | 1 | `internal/isonet/toxiproxy_integration_test.go` ran automatically, because Toxiproxy answered on :8474 (it does whenever `make up` is running). |
    | 2 | The test signed on as the lab acquirer 970499, toggled the issuer proxy (which also dropped the real gateway's connection; the gateway reconnected), and signed off when it ended. |
    | 3 | The issuer keeps sign-on state per acquirer (`acquirer_link`), so the test's sign-off marked the real gateway's live link DISCONNECTED. |
    | 4 | The issuer answered **91** to every 0200 and 0420. |
    | 5 | The 0210 carrying 91 had no valid MAC, so the gateway treated it as a MAC failure: RC 96 plus a queued reversal, which also got 91. |
    | 6 | Echoes are answered regardless of sign-on state, so the gateway never noticed and never signed on again. |

    **Fix:**
    - When `Supervisor.Send` gets RC 91 on any request other than a network-management 08xx message, it asks the connection loop, which owns the connection, to sign on again. The request goes through a one-slot channel with a non-blocking send.
    - Tests that drive the real stack (`isonet`, `chaos`) now run only with `MCN_STACK_TESTS=1`. CI has no Toxiproxy and skipped them before.
    - `echoTick` was extracted to keep `runOnce` under the gocyclo limit.

    **Recovery on the live stack:** the gateway signed on again, and the 5 stuck reversals were delivered (SAF: 8 ACKED, 0 pending).

    **Tests:**
    - `TestSupervisor_signsOnAgainWhenTheIssuerAnswersNotSignedOn__MCN_202` uses a fake issuer that keeps per-acquirer sign-on state like the real one.
    - A full `go test ./...` with the stack up now leaves `acquirer_link` SIGNED_ON.

### Tooling (PLAT)

13. **`land-pr.sh` merged before CI when no rebase was needed.**
    - **Cause:** the CI wait only ran after a rebase. Landing #90 right after opening it hit pending checks, and the merge was refused.
    - **Fix (#91):** the script always waits for the CI run of the exact commit being merged: the PR's head, or the pushed commit after a rebase, since `headRefOid` lags a push. `gh pr checks --watch` also waits for third-party checks such as GitGuardian.

## How to test

```bash
make up && make seed
cd web-next && pnpm dev          # real mode goes through the BFF; no NEXT_PUBLIC_API_BASE_URL
# open /pos and /transactions (?view=approved|declined|reversed), toggle Dễ hiểu / Chuyên sâu

curl -s localhost:8080/v1/transactions/<rrn>/journey | python3 -m json.tool   # codes, actors, messages
curl -s localhost:3000/api/v1/cards                                          # issuer card API through the BFF
docker exec mini-card-network-postgres-1 psql -At -U issuer -d issuer -c "select status from acquirer_link"
```

Per lane:
- `cd gateway-go && CGO_ENABLED=0 go test -count=1 ./...` is safe with the stack up. Add `MCN_STACK_TESTS=1` to also run the Toxiproxy integration tests, which sign the running gateway off.
- `cd web-next && pnpm lint && pnpm test && pnpm build`.
- `make contracts`.

## Still open

- **Issuer card ETag.** `CardAdminController.etagFor` hashes only the limits, so every card without limits has the same ETag, `sha256("")`. A client that calls the issuer directly with `If-None-Match` gets a 304 after its balance changed. Browser traffic is safe through the BFF. Fix: `Cache-Control: no-store` on the card GETs.
- **A balance inquiry on the real stack declines RC 30** (format error), found while checking the POS. A gateway/issuer packing issue; the POS shows it as a generic decline.
- **The dev:mock POS tiles show fixed fixture balances.** The POS mocks track spending in memory, so the tiles don't go down after a payment in `dev:mock`. The real stack is correct.
- **MockProvider starts two MSW workers under React StrictMode.** The POS mocks replay by `Idempotency-Key`, so a payment is still applied once.
- **The timeout journey wasn't run live**, because forcing one needs the DROP_RESPONSE chaos scenario on the shared stack. It is covered by unit tests and an api test against the contract.
- **Deviations from the canvas**, all deliberate:
  - The POS shows 6 cards, 3 per row, and has the transaction-type row.
  - Chip reads DE 22 `052` (no PIN) where the canvas shows `051`.
  - The Journey tabs are real outcomes, not the canvas's three fixed stories.
  - The money rows aren't timestamped.
- **Carried over from R5.1:** G1 (`/v1/network/switch`), G3 (`transaction.updated`), G5, G7 and R-12.
