# MCN-403 Late response handling — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans with superpowers:test-driven-development. Worktree `../mcn-worktrees/gw-403-late-response`, branch `feat/MCN-403-late-response`. Requires MCN-401 merged (`tran_log.late_response_code`/`late_response_at` columns already added by MCN-401's `migrations/00003_saf_queue.sql`; `journey.go`'s `KindWarn` already exists).

**Goal:** A 0210 that arrives for a transaction no longer in `SENT` (it already timed out and moved on) is recorded — `late_response_code`/`late_response_at` — and surfaced as a metric and a network event, but never flips the transaction's already-final status.

**Architecture:** `internal/isonet.Mux`'s response-matching path (the same place MCN-203 already detects "response arrived after our own `ctx` timeout fired" — confirmed by `obs.LateResponseTotal`, defined in `metrics.go` referencing "MCN-203-AC3 — detection only, reversal/SAF queuing is a later story") gets one addition: instead of silently dropping the late match, it now calls a new `purchase.Service.RecordLateResponse(ctx, rrn string, responseCode string) error` (looked up via the RRN embedded in the matched STAN/response). `RecordLateResponse` checks the transaction's current `tran_log.state`; if it is `SENT` this is a normal on-time response (not this story's path — leave alone), otherwise `UpdateLateResponse` sets the two new columns, increments `obs.LateResponseTotal` (already registered, just needs its `.Inc()` call added where the actual detection happens), and broadcasts a `WARN` network event via the same broadcaster MCN-401's dead-letter path uses. `journey.BuildJourney` grows one more `buildStep`-adjacent synthetic step when `LateResponseAt` is non-nil.

**Tech Stack:** Go 1.24, existing `internal/isonet`, `internal/purchase`, `internal/journey`, `internal/store`.

**Spec:** `docs/03-iso8583-interface-spec.md` §7.3/§9, `docs/06-user-stories.md` MCN-403.

## Global Constraints

- Recording a late response never changes `tran_log.state` — the transaction is already final (`TIMED_OUT`, `REVERSAL_PENDING`, or `REVERSED` by the time a late 0210 shows up); only the two new columns and the journey/metric/event side effects change.
- `late_response_code`/`late_response_at` already exist (MCN-401's migration `00003_saf_queue.sql`) — this story adds no migration.

## Ruling: where "late" is actually detected

`internal/isonet.Mux` matches responses to pending requests by `(STAN, DE 7)` and already has to handle "no pending request found for this STAN" as *some* outcome once a request's own `ctx` has expired — confirm the exact current behavior (grep `mux.go` for what happens today when a response arrives with no matching pending entry) before writing `RecordLateResponse`'s caller: if `Mux` currently just drops it with a log line, this story adds a callback hook (`Mux.OnLateResponse func(rrn, responseCode string)`, set once in `main.go` to call `purchaseService.RecordLateResponse`) rather than making `internal/isonet` import `internal/purchase` directly — `isonet` must stay domain-agnostic (it doesn't know what a "transaction" is), so the hook is a plain function value, not an interface pulling in the purchase package's types.

func (r *TranLogRepository) UpdateLateResponse(ctx context.Context, id int64, responseCode string) error {
	_, err := r.pool.Exec(ctx,

	return err
}
