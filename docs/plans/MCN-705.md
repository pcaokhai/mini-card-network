# MCN-705 Settlement screen — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans with superpowers:test-driven-development. Worktree `../mcn-worktrees/web-705`, branch `feat/MCN-705-settlement-screen`. Requires MCN-003 (MSW mocks) merged, unchanged otherwise. **MSW-mocks-first, per root `CLAUDE.md` §5's "frontend never waits for backend" rule**: this story is pulled into Sprint 8 ahead of its slice-mates MCN-702 (cutover/0500 reconciliation) and MCN-704 (reconciliation/breaks/clearing file), both Sprint 9 — `docs/07-delivery-plan.md`'s Slice S7 pairs MCN-702/MCN-704 (backend) with MCN-705 (frontend) on release R7, but the Sprint 8 wave table places only MCN-705 this sprint. The screen is built and fully tested entirely against MSW mocks (`web-next/src/mocks/generated/handlers.ts:533-849`, already generated from `contracts/openapi.yaml`'s settlement paths — confirmed present before writing this plan) and shows placeholder/empty states for any real-data path MCN-702/704 haven't implemented yet; switching to the real backend later is a config flag only (`NEXT_PUBLIC_API_MOCKS=false`, per `docs/07-delivery-plan.md` §9.5), not a code change to this story's components.

**Goal:** A four-step wizard driven by `SettlementDay.stage`; a totals table with match badges; a breaks list with resolve actions; a clearing-file card. Generating the clearing file with open breaks shows the API's problem-detail response inline with a shake animation.

**Architecture:** A new `settlement-client.ts` (mirrors `security-client.ts`/`pos-client.ts`'s exact `openapi-fetch` + TanStack Query shape — `createClient<paths>`, a `liveFetch` thunk for MSW compatibility, one hook per endpoint) wraps `contracts/openapi.yaml`'s five already-scaffolded settlement paths: `useSettlementDay(businessDate)` (`GET /v1/settlement/days/{businessDate}`), `useCutover(businessDate)` (`POST .../cutover`), `useReconciliation(businessDate)` (`POST .../reconciliations`), `useBreaks(businessDate)` (`GET .../breaks`), `useResolveBreak(breakId)` (`POST /v1/settlement/breaks/{breakId}/resolutions`), `useGenerateClearingFile(businessDate)` (`POST .../clearing-files`). A new `web-next/src/components/settlement/` directory (sibling to `security/`, `pos/`, `cards/` — one component per file, per root `web/coding-style.md`'s file-organization rule) holds: `SettlementWizard` (the four-step shell, steps derived from `SettlementDay.stage`'s enum — confirm the exact `SettlementStage` values from `contracts/openapi.yaml`'s schema before hardcoding step labels, Task 1), `TotalsTable` (renders `SettlementDay.totals: TotalsRow[]`, one row per side with a match/mismatch badge computed client-side from whether the acquirer and issuer rows for a given metric agree — no new field needed, `TotalsRow`'s existing shape already carries what's needed per side), `BreaksList` (renders `ReconBreak[]` from `useBreaks`, each row's `resolution` field drives a resolve button that's disabled once `resolution !== "OPEN"`), `ClearingFileCard` (renders `SettlementDay.clearingFile` when non-null, else a "not yet generated" placeholder state — MCN-702/704 not landing this sprint means `clearingFile` and `openBreaks`/`matchedCount` will show whatever the MSW fixture returns, which this plan does not need to special-case since the mock server already returns a complete `SettlementDay` shape). The shake-on-problem-detail behavior (AC2) reuses whichever existing shake/error-inline pattern the codebase already has (grep `web-next/src/components/**/*.css` for an existing `shake`/`@keyframes` — `PinBlockVisualiser.tsx`'s security screen or a POS validation-error component is the likely precedent; reuse the same animation name/duration rather than defining a second one, per DRY and root `web/coding-style.md`'s CSS-custom-property convention).

**Tech Stack:** Next.js App Router, TypeScript strict, `@tanstack/react-query`, `openapi-fetch`, MSW (existing generated handlers), Playwright (visual/E2E, deferred to the Sprint 8 integration checkpoint per `SPRINT-8.md`, not this plan's own scope beyond component tests), Vitest/Testing Library for component tests.

**Spec:** `docs/06-user-stories.md` MCN-705-AC1/AC2, `contracts/openapi.yaml:429-484` (the five settlement paths), `contracts/openapi.yaml:816-849` (`SettlementDay`, `ReconBreak`, `ClearingFile` schemas — already read in full for this plan), root `CLAUDE.md` §5 ("Frontend never waits for backend... Switching to the real backend is a config flag, not a code change"), `docs/10-web/design-quality.md`/`docs/10-web/patterns.md` (anti-template policy, compound-component/container-presentational patterns already used by `security`/`pos` components — this plan follows the same conventions, not new ones).

## Global Constraints

- No component in this plan makes a direct `fetch` call — every network access goes through `settlement-client.ts`'s hooks, matching `security-client.ts`/`pos-client.ts`'s existing convention exactly.
- `liveFetch`'s thunk pattern (`(...args) => globalThis.fetch(...args)`) is copied verbatim from `security-client.ts`'s existing comment/implementation — `openapi-fetch`'s `createClient` reads `globalThis.fetch` once at call time, before MSW patches it in tests, so every hook passes `{ fetch: liveFetch }` explicitly, never relying on the client's default.
- Every mutating hook (`useCutover`, `useReconciliation`, `useResolveBreak`, `useGenerateClearingFile`) invalidates the relevant `useQuery` cache key on success (`["settlement", "day", businessDate]`), matching `security-client.ts`'s `useStartRotation` invalidation pattern — no manual `refetch()` calls scattered through components.
- Money fields (`Money.amount`) are rendered via whatever existing minor-units-to-display-string formatter the codebase already has (grep `web-next/src/shared` for a `formatMoney`/`formatAmount` utility used by `pos`/`cards` components) — no new formatting logic invented, no floating-point division introduced in display code.

## Ruling 1: this sprint's scope is the wizard shell and MSW-driven states, not real cutover/reconciliation logic

MCN-702 (cutover + 0500 reconciliation, gateway+issuer) and MCN-704 (reconciliation `reconcile()`, breaks, clearing file generation, settlement) are both Sprint 9 stories — neither exists yet. This plan's `useCutover`/`useReconciliation`/`useResolveBreak`/`useGenerateClearingFile` hooks call real, already-scaffolded contract endpoints, but against MSW mocks only this sprint (the same "groundwork against the fake issuer, not real logic" framing `MCN-603.md`'s Ruling 1 used for gateway advanced-transaction endpoints in Sprint 7) — this plan's own integration/component tests assert against the MSW fixture's scripted responses, never against a running `settlement/` service. The Sprint 8 integration checkpoint (`SPRINT-8.md`) does not include a real-backend settlement journey for this reason, and this plan's PR description states that explicitly so a reviewer doesn't assume more was proven than was.

## Ruling 2: `SettlementStage` step labels and `BreakType`/`ReconBreak.resolution` enums are read from `contracts/openapi.yaml`, never re-derived

The four-step wizard's steps map 1:1 to whatever `SettlementStage`'s enum values actually are in `contracts/openapi.yaml` (Task 1 greps and pins the exact values before writing `SettlementWizard` — this plan does not guess step names like "Cutover/Reconcile/Review/File" without confirming against the real schema first, since a mismatch here would mean the wizard's step indicator silently drifts from what `SettlementDay.stage` the mock/real backend actually returns).
