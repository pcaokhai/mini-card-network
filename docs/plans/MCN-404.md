# MCN-404 Chaos API — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans with superpowers:test-driven-development. Worktree `../mcn-worktrees/gw-404-chaos-api`, branch `feat/MCN-404-chaos-api`. Requires MCN-401 merged (`purchase.Service`, `saf.Worker`, `journey`'s `REVERSAL`/`WARN` vocabulary). Package lives at `internal/chaos` per `gateway-go/CLAUDE.md`'s layout table ("chaos/ — Toxiproxy admin client").

**Goal:** `GET /v1/chaos/scenarios` / `PUT /v1/chaos/scenarios/{id}` toggle six named failure scenarios against the real Toxiproxy instance (`infra/docker-compose.yml`'s `toxiproxy` service, admin API at `localhost:8474`, same admin endpoint `toxiproxy_integration_test.go` already talks to); `POST /v1/chaos/runs` fires N synthetic purchases against seed cards from `contracts/fixtures/cards.json` and ends with a money-conservation check (`opening − approved + reversed = closing`, discrepancy must be `0`); `chaos.changed` and `chaos.run.progress` are broadcast over the existing WS hub.

**Architecture:** `internal/chaos.ToxiproxyClient` wraps the six `ChaosScenarioId` values (`SLOW_NETWORK`, `CONNECTION_CUT`, `DROP_RESPONSE`, `DUPLICATE_REQUEST`, `ISSUER_DOWN`, `LATE_RESPONSE`) as a fixed map to Toxiproxy toxic names/types on the one proxy the issuer link already goes through (confirm the proxy name Toxiproxy is configured with — `infra/toxiproxy/` config file — before hardcoding it). `internal/chaos.Runner` drives a `ChaosRun`: for `requested` transactions, resolves `openingBalanceTotal` (sum of seed cards' balances, read once via the same `contracts/fixtures/cards.json` `internal/purchase.CardTokenRegistry` already embeds — no new fixture reader), fires purchases through the existing `purchase.Service.CreatePurchase` (reusing the exact same code path a real POS uses — chaos is injected at the network layer via Toxiproxy, not by mocking the service), tracks approved/declined/reversed counts from each `Transaction.Status`, and once all `requested` have settled (including any SAF reversals draining — poll `saf_queue` depth via `SafRepository.ListPending` until it's back to the pre-run baseline, capped at a generous timeout), reads `closingBalanceTotal` the same way and computes `ledgerDiscrepancy`.

**Tech Stack:** Go 1.24, existing `internal/purchase`, `internal/saf`, `internal/ws`, `net/http` client to Toxiproxy's admin API (no new dependency — same raw `http.Client`+JSON pattern `toxiproxy_integration_test.go` already uses).

**Spec:** `docs/06-user-stories.md` MCN-404, `contracts/openapi.yaml` (`ChaosScenario`, `ChaosScenarioId`, `ChaosRun`), `contracts/ws-events.schema.json` (`chaos.changed`, `chaos.run.progress` payload shapes).

## Global Constraints

- `openingBalanceTotal`/`closingBalanceTotal`/`ledgerDiscrepancy` are `int64` minor units, per `ChaosRun`'s OpenAPI schema (`format: int64`).
- A chaos run only ever touches the fixed set of seed cards from `contracts/fixtures/cards.json` — never a production-shaped card — so a discrepancy is unambiguous (no other traffic touches those accounts during a run; document this single-writer assumption in the Ruling below rather than building run isolation infrastructure YAGNI doesn't need yet).
- Toxiproxy toxics are reset to disabled between runs / at gateway startup so a crashed run doesn't leave a permanent failure injected — `ToxiproxyClient` exposes `DisableAll(ctx) error`, called once in `main.go` at boot.

## Ruling: scenario → Toxiproxy toxic mapping

| `ChaosScenarioId` | Toxiproxy toxic | Notes |
| --- | --- | --- |
| `SLOW_NETWORK` | `latency` toxic, `latency: 3000`, `jitter: 0` | matches docs/06's "latency 3000 ms" |
| `CONNECTION_CUT` | `reset_peer` toxic | TCP RST mid-connection |
| `DROP_RESPONSE` | not a Toxiproxy toxic — handled by a `fake-issuer mode` flag the gateway's own dev/chaos issuer-simulator path already needs for MCN-407's suite; confirm before this story whether that simulator exists yet (`grep -rl "fake.*issuer\|FakeIssuer" gateway-go/internal` and `issuer-jpos`). If it does not exist yet, this scenario is scoped to a stub that returns `501 Not Implemented` from `PUT /v1/chaos/scenarios/DROP_RESPONSE` with a clear `Problem` body naming the missing dependency, and MCN-407 (Sprint 6) is the story that actually builds the fake-issuer response-dropping mode — do not build a duplicate simulator here just to unblock one enum value. |
| `DUPLICATE_REQUEST` | Toxiproxy `slicer` is not the right primitive for a full duplicate; implemented gateway-side: when enabled, `purchase.Service` (via a `chaosHooks` port checked once, no-op otherwise) sends the same 0200 twice with the same STAN, exercising the issuer's `Deduplicate` participant end-to-end | |
| `ISSUER_DOWN` | `reset_peer` toxic on the whole link | reuses `CONNECTION_CUT`'s mechanism at the connection level (same toxic type is fine — the two scenarios differ in narrative/easyText, not in mechanism, until a real "process down" simulation exists) |
| `LATE_RESPONSE` | `latency` toxic with a delay exceeding `docs/03` §9's 30 s request timeout | exercises MCN-403's late-response path directly |
