**Goal:** The POS screen (`PosScreen.tsx`) gains a transaction-type selector (purchase, pre-auth, completion, refund, balance) that shows only the fields each type needs; the Cards screen's existing `HoldsList` shows every hold (not just `ACTIVE`) with its expiry and completion state visible.

**Architecture:** `PosScreen.tsx` gains a `TransactionTypeSelector` (`@/components/pos/TransactionTypeSelector.tsx`, new) driving a discriminated-union form state (`{type: 'PURCHASE'|'PREAUTH'|'REFUND'|'BALANCE'} & CardPresentFields` vs `{type: 'COMPLETION', rrn: string, amount: Money}` — completion has no card-present fields per `contracts/openapi.yaml`'s `createCompletion` request, which is just `{amount}` keyed by the `rrn` path param, confirmed by re-reading the contract before writing this plan) so the amount/PIN/card fields conditionally render per type rather than one form silently sending irrelevant fields. `src/shared/api/pos-client.ts` (existing, backs `useCreatePurchase`) gains four sibling hooks — `useCreatePreAuth`, `useCreateCompletion`, `useCreateRefund`, `useCreateBalanceInquiry` — following `useCreatePurchase`'s exact existing shape (same `openapi-fetch` + `useMutation` pattern), typed from the generated OpenAPI schema, no hand-rolled request/response types (same convention `MCN-505.md`'s Ruling 2 established for `security-client.ts`). `HoldsList.tsx` (existing, `src/components/cards/HoldsList.tsx`) is extended, not rewritten: it currently filters to `ACTIVE` only and renders three columns; this plan removes the `ACTIVE`-only filter and adds a status pill column (reusing whatever status-pill visual convention `network/LinkStatusPill.tsx` already established, per web/design-quality's "reuse before invent" and this repo's own precedent of one pill component style per status-bearing entity) so `COMPLETED`/`RELEASED`/`EXPIRED` holds remain visible with their outcome, not just active ones.

**Tech Stack:** Next.js App Router, TypeScript strict, `@tanstack/react-query`, `openapi-fetch`, `next-intl`.

**Spec:** `docs/06-user-stories.md` MCN-604-AC1/AC2, `contracts/openapi.yaml:44-99` (the four new transaction endpoints' request/response shapes), `:558-568` (`Transaction` schema — `approvedAmount`, `balance`, `originalRrn`), existing `HoldsList.tsx`'s `Hold` type (`status: "ACTIVE"|"COMPLETED"|"RELEASED"|"EXPIRED"`, already covers the states this story needs to surface), `web-next/src/app/(console)/network/LinkStatusPill.tsx` (the existing status-pill convention this plan reuses for hold status).

## Global Constraints

- `TransactionTypeSelector`'s five types are a closed, named union (`type TransactionType = "PURCHASE"|"PREAUTH"|"COMPLETION"|"REFUND"|"BALANCE"`) — no stringly-typed `string` field for transaction type anywhere in the new form state.
- Completion's form never renders card-present fields (no `CardPicker`, no `PinPad`) since its request shape has none — a completion only ever needs `rrn` + `amount`, and rendering irrelevant fields would silently invite a user to fill in data the request never sends (a genuine correctness/UX bug MCN-604-AC1 exists to prevent, not just a cosmetic simplification).
- All five `pos-client.ts` hooks (`useCreatePurchase` existing + four new) share the same MSW-backed test setup and `openapi-fetch` client instance — no second HTTP client construction.
- `HoldsList`'s status pill reuses `LinkStatusPill`'s existing visual/accessibility pattern (confirm its real prop shape before reusing) rather than a new one-off pill component.

## Ruling 1: one `TransactionTypeSelector` + conditional field rendering, not five separate screens

`docs/06-user-stories.md`'s MCN-604-AC1 says "POS transaction-type selector ... with correct fields per type" — a single screen with type-driven conditional rendering, not five separate routes/screens, matching the existing `PosScreen.tsx`'s single-screen shape (it already conditionally shows `ScenarioButtons`/`CardPicker`/`PinPad` based on state) and avoiding a premature multi-route split for what is fundamentally one form with a discriminated field set (YAGNI — a route-per-type split would only be justified if each type needed materially different layout/navigation, which none do here).
