Slice **S5** (`docs/07-delivery-plan.md` §2), flag `FF_S5_KEYS`.

**Goal:** A Security and Keys screen shows every key (issuer + acquirer) as a table with KCV, a lifetime bar, and an expiry warning; a rotation stepper renders `KeyRotation.steps[]` live; a PIN block visualiser illustrates ISO 9564-1 format 0 in the browser (clearly labelled as illustration only); a PCI "never do" list renders in Easy/Expert wording.

**Architecture:** `src/app/(console)/security/SecurityScreen.tsx` (new route, same `page.tsx` re-export pattern as `cards/page.tsx`) composes four components under `src/components/security/`: `KeyTable.tsx` (fetches `GET /v1/keys/acquirer` + `GET /v1/keys/issuer` via two `useQuery` hooks, same `openapi-fetch` + `@tanstack/react-query` pattern as `cards-client.ts`'s `useCards`), `KeyLifetimeBar.tsx` (reuses `LimitsSliders.tsx`'s `UsageBar` pattern — a `scaleX` transform on a filled bar, not a new charting primitive, per web/design-quality's "reuse before build"), `RotationStepper.tsx` (drives `POST .../rotations` then polls `GET .../rotations/{id}` via `useMutation` + `useQuery` with a `refetchInterval`, rendering the four `KeyRotation.steps[]` entries as a horizontal stepper), `PinBlockVisualiser.tsx` (reuses `src/components/pos/pinblock.ts`'s existing `buildPinBlock` function directly — computed in the browser over test-fixture PAN/PIN values only, never called with a real captured value, and the panel is headed with an explicit "Illustration only — not real encryption" label per MCN-505-AC2), `PciNeverDoList.tsx` (a static, mode-aware list reading the existing Easy/Expert mode context already used elsewhere in `web-next`, e.g. `TransactionSummary.responseLabel`'s "Plain-language label for Easy mode" convention — grep the mode-switch hook before writing).

**Tech Stack:** Next.js App Router, TypeScript strict, `@tanstack/react-query`, `openapi-fetch`, `next-intl`, MSW (tests).

**Spec:** `docs/06-user-stories.md` MCN-505-AC1/AC2/AC3, `contracts/openapi.yaml:778-806` (`KeyInfo`, `KeyRotation` schemas), `:407-426` (rotation endpoints), `docs/03-iso8583-interface-spec.md` §11 (PIN block format 0, exact formula already implemented in `pinblock.ts`), root `CLAUDE.md` §6 rule 2 (PCI DSS — the visualiser is explicitly labelled illustration-only, never wired to a real PAN/PIN capture flow), rules `~/.claude/rules/web/design-quality.md` (anti-template policy — this plan reuses `UsageBar`'s existing visual language rather than inventing a new component style for the lifetime bar).

## Global Constraints

- `PinBlockVisualiser` never accepts a real card's PAN from application state — only a hardcoded test-fixture PAN from `contracts/fixtures/cards.json` or a user-typed illustrative value, both visibly labelled; it must never be wired to any live transaction flow.
- The rotation stepper's step names (`GENERATE`, `SEND_0800_161`, `PARTNER_CONFIRM`, `ACTIVATE`) come directly from `KeyRotation.steps[].name` — no separately-invented UI label set that could drift from the backend vocabulary (`MCN-504-GW.md`'s Ruling 1).
- No new dependency: `UsageBar`'s CSS-transform bar, `pinblock.ts`, `openapi-fetch`/`react-query`, and `next-intl` are all already in the project (rung 2 of the ladder — reuse before adding a library).
- All new visible strings go through `next-intl`, matching `LimitsSliders.tsx`'s `useTranslations("cards.limits")` convention — this screen adds a `security` namespace.

## Ruling 1: rotation stepper polls, it doesn't own a WebSocket channel

`ws-events.schema.json` has no `key_rotation.*` event type (confirmed by grepping it before writing this plan) — MCN-504 doesn't add one, and this plan doesn't invent a WS contract unilaterally on the frontend side (contract changes are a separate PR per root `CLAUDE.md` §9, and no such PR is scheduled this sprint). `RotationStepper` instead polls `GET /v1/keys/acquirer/rotations/{rotationId}` with `useQuery`'s `refetchInterval: 1000` while `status === 'RUNNING'`, stopping once `COMPLETED`/`FAILED` (same short-poll pattern already acceptable for a four-step, sub-minute-duration resource — a full WS event is unwarranted machinery for something this short-lived, following YAGNI).

## Ruling 2: mock shape parity with the real `MCN-504-GW.md` resource, once it merges

The MSW mocks (`web-next/src/mocks/generated/handlers.ts`) are generated directly from `contracts/openapi.yaml`'s `KeyRotation` schema — the same schema `MCN-504-GW.md` implements against server-side. Since both sides derive from the same OpenAPI source of truth, there is no separate "mock shape" to keep in sync by hand; this plan's only obligation is to never hand-write a second, divergent shape for `KeyRotation`/`KeyInfo` in component code — all typing comes from `@/shared/api/generated/schema`'s `components["schemas"]["KeyRotation"]`/`["KeyInfo"]`, generated types, never a hand-rolled interface (confirmed as the existing convention via `cards-client.ts`'s `CardSummary`/`CardDetail` type aliases).
