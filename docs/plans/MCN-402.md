# MCN-402 Issuer reversal, advice and duplicate handling — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans with superpowers:test-driven-development. Worktree `../mcn-worktrees/iss-402-reversal`, branch `feat/MCN-402-reversal`. Requires MCN-302 merged (`Authorize`, `LogAndOutbox`, `TranLogRepository`, `LedgerRepository`, `AuthorizationListener`, `iso-txn-mgr`). This story adds a **second** jPOS `TransactionManager` chain dedicated to MTI class `04` (advices), parallel to `iso-txn-mgr`, because a reversal's participant chain (locate original, post reversing journal, always-ACK) is materially different from a purchase's (`ParseAndValidate → Deduplicate → CheckCard → CheckLimits → Authorize`) — reusing `iso-txn-mgr` for both would force every purchase participant to branch on MTI, which `docs/10-engineering-standards.md` §7 (extend by adding, not by editing switch statements) argues against.

**Goal:** A 0420/0421 (reversal advice) or 0421 repeat locates its original transaction via DE 90, posts a reversing double-entry journal and marks it `REVERSED` when found, records `REVERSAL_WITHOUT_ORIGINAL` when not found (so a later-arriving original is declined RC `94`), replays a stored response byte-for-byte on any duplicate, and always answers with 0430 — advices are never declined. A property-style test proves any interleaving of {original, duplicate, reversal, repeat} leaves the ledger's Σ debits = Σ credits.

**Architecture:** `io.mcn.issuer.adapter.iso.ReversalListener` (new, parallel to `AuthorizationListener`) accepts MTI class `04` on the same `NACChannel`/`QServer` (`30_iso_server.xml`), rejects on a link that isn't signed on exactly like `AuthorizationListener` does, and queues into a new `reversal-txn-mgr` (`50_reversal_txn_manager.xml`) instead of `iso-txn-mgr`. Four new participants run there: `ParseReversal` (extracts DE 90's four components), `DeduplicateReversal` (dedupe key = DE 90 verbatim, per `docs/03` §7.3's "a reversal of an already reversed transaction is acknowledged idempotently with no ledger effect"), `LocateAndReverse` (the domain core: finds the original by DE 90 in `tran_log`, posts the reversing journal via a new `LedgerRepository.postReversal`, sets `tran_log.status = REVERSED`, or — not found — inserts a `REVERSAL_WITHOUT_ORIGINAL` row keyed by DE 90 so a later original can be declined), `RespondReversal` (always sends 0430; `AbortParticipant`, same pattern as `Respond`, because advices are never declined). `Authorize`'s existing "declined RC 94 for a duplicate transmission" path is extended in `Deduplicate` (the *purchase* chain): before running its existing `findByDedupeKey` lookup, it also checks a new `reversal_without_original` table for a matching DE 90 key and, if found, short-circuits straight to RC `94` without running `CheckCard`/`Authorize` at all.

**Tech Stack:** Java 25, jPOS Q2 3.0.1, Hikari/JDBC (no ORM, matching `TranLogRepository`'s existing plain-JDBC style), JUnit 5 (no new property-testing dependency — see Ruling 2).

**Spec:** `docs/03-iso8583-interface-spec.md` §7.3 (0420/0421/0430 semantics, DE 90 layout, "reversal of an already-reversed transaction is idempotent with no ledger effect"), §8 (RC `94` duplicate transmission), `docs/05-data-model.md` §3 (double-entry rules), `docs/06-user-stories.md` MCN-402.

## Global Constraints

- Every write to `journal_entry`/`ledger_posting` for a reversal happens inside the exact same JDBC transaction as the `tran_log.status = REVERSED` update — same discipline as `Authorize` (MCN-302b): one explicit `Connection`, `setAutoCommit(false)`, commit once at the end.
- 0430 is **always** sent, whatever `LocateAndReverse` decides (found, not-found, or already-reversed) — `RespondReversal` never inspects a response-code context key the way `Respond` does; per spec, "Advices cannot be declined."
- Money stays `long` minor units throughout; no new money type.
- No PAN ever appears in a reversal's `tran_log`/`journal_entry` row beyond what the original row already had (a reversal never re-sends DE 2; it's looked up by DE 90, not by card).

## Ruling 1: `ReversalListener` — a second listener, not a branch inside `AuthorizationListener`

`AuthorizationListener.process()` currently returns `false` for anything outside MTI class `01`/`02` (`mtiClass` check), so QServer's document-order dispatch (`30_iso_server.xml`'s comment: "stops at the first listener whose `process()` returns true") already falls through past it for class `04` — no change needed to `AuthorizationListener` itself. Add `ReversalListener` as a third `<request-listener>` in `30_iso_server.xml`, filtering on `mtiClass.equals("04")`, queueing into `reversal-txn-mgr` by name (new `NameRegistrar` lookup, mirroring `AuthorizationListener.transactionManager()` verbatim). This is additive (new class + new XML block), matching the "extend by adding" rule (`docs/10-engineering-standards.md` §7) better than teaching one listener two unrelated dispatch paths.

## Ruling 2: property-based test without a new dependency

`build.gradle` has no jqwik/QuickCheck-style library today, and one story's single test doesn't justify a new dependency + its license review (`CLAUDE.md` §9: "do not add a dependency without noting it in the plan with its purpose and license"). Instead, Task 6 writes a manual randomized JUnit 5 test: for N=200 iterations, generate a random shuffled ordering of `{original, duplicate-of-original, reversal, repeat-of-reversal}` for a fresh synthetic transaction each iteration (seeded `java.util.Random` for reproducibility — log the seed on failure), drive each event through the real participant chains against a Testcontainers Postgres, and after all four events assert `Σ ledger_posting.amount WHERE side='D' == Σ ledger_posting.amount WHERE side='C'` for that transaction's `journal_entry` rows. This is the same invariant `docs/06` MCN-401-AC4/MCN-407 chaos runs check at a larger scale — this test checks it at the single-transaction, all-interleavings scale.

## Ruling 3: dedupe key for a reversal vs. `REVERSAL_WITHOUT_ORIGINAL` lookup key

Both use DE 90's four components (original MTI, original STAN, original DE 7, original acquirer ID) plus the reversal's *own* business date — never the original transaction's business date, since a reversal can arrive on a later business date than its original. `DeduplicateReversal`'s dedupe key is therefore `(own mti='0420', DE90-4-tuple, own business_date)` — two reversals for the same original on the same business date are the duplicate case; a repeat (`0421`) is *not* a new dedupe key event, it is recognized by `LocateAndReverse` checking `tran_log`'s prior `REVERSED`/`REVERSAL_WITHOUT_ORIGINAL` state for the same DE90 tuple and no-op'ing with 0430 (per spec: "reversal of an already-reversed transaction is acknowledged idempotently with no ledger effect") — `DeduplicateReversal` only catches an exact byte-identical resend (matching STAN of the *reversal itself*, not the repeat), while `LocateAndReverse`'s own idempotency check catches the semantic repeat. Both checks are needed; they are not redundant.
