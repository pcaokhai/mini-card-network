# MCN-308 Issuer Admin API — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans with superpowers:test-driven-development. Worktree `../mcn-worktrees/iss-308-admin-api`, branch `feat/MCN-308-admin-api`. Requires MCN-302b merged (real ledger, `AccountLockRepository`/`LedgerRepository`).

**Goal:** `GET /v1/cards`, `GET /v1/cards/{cardRef}` (with `ETag`), `POST/DELETE /v1/cards/{cardRef}/blocks`, `PUT /v1/cards/{cardRef}/limits` (with `If-Match`), `GET /v1/cards/{cardRef}/ledger` — a small REST Admin API on the issuer so operators can manage cards and see the ledger, with optimistic concurrency and an audit trail on every write.

**Architecture:** A plain HTTP server (this project's existing Admin API convention — check MCN-005-ISS's actual choice, `docs/02-software-architecture.md` names Javalin for the issuer's admin surface per earlier sprints' work) exposes `/v1/cards*` routes backed by `CardRepository`/`AccountLockRepository`/`LedgerRepository` (MCN-301/302b) plus a new `CardLimitRepository`/`AuditLogRepository`. `cardRef` is an opaque external identifier (`docs/05` §3's "external references are opaque" rule) — this story adds a `card.card_ref` column if one doesn't already exist (check MCN-301's migration first; if `CardRepository` currently only exposes internal `id`, add the opaque ref there rather than exposing the internal `BIGSERIAL` id in any API response). `ETag`/`If-Match` map directly to `account.version`/`card`'s own version concept — confirm exactly which row's version the ETag represents (the card's limits, most likely, since that's what `PUT .../limits` modifies) before wiring it.

**Tech Stack:** Java 25, whatever HTTP framework MCN-005-ISS already established for the Admin API (Javalin, per architecture doc references — confirm the real merged choice before assuming), JDBC.

**Spec:** `contracts/openapi.yaml` (`/v1/cards*`, `CardSummary`/`CardDetail`/`CardLimits`/`JournalEntry`), `docs/04-api-contract.md` (idempotency: `Idempotency-Key` required on every state-changing call, 422 on key-reuse-with-different-body; concurrency: `ETag`/`If-Match`, 412 on mismatch), `docs/05-data-model.md` (`idempotency_record` for the issuer, per its §4 delta table entry for MCN-308), `docs/06-user-stories.md` MCN-308.

## Global Constraints

- Every write endpoint (`POST/DELETE blocks`, `PUT limits`) requires `Idempotency-Key`; a replay with an identical body returns the stored response, a replay with a different body returns 422 `idempotency-key-mismatch` per `docs/04` §2's exact problem-type vocabulary — reuse those exact problem `type` strings, don't invent new ones.
- `PUT .../limits` requires `If-Match`; a stale ETag returns 412 `precondition-failed`.
- Every block/unblock/limit-change writes one `audit_log` row (`actor`, `action`, `entity_type`, `entity_id`, `before_state`, `after_state` as JSONB) in the same transaction as the state change — `audit_log` is append-only (its `trg_audit_immutable` trigger, from MCN-301's baseline migration, already enforces this at the DB level).
- No raw PAN in any Admin API response — `CardSummary.maskedPan` only.

## Ruling: `card_ref` as the opaque external identifier

`CardRepository` (MCN-301) currently keys everything by the internal `BIGSERIAL id`. Per `docs/05-data-model.md` §3's "IDs: internal BIGINT identities; external references are opaque... never expose internal IDs in APIs" rule, this story adds a `card_ref` column (`V4__card_ref.sql`, a short migration: `ALTER TABLE card ADD COLUMN card_ref TEXT NOT NULL DEFAULT gen_random_uuid()::text; CREATE UNIQUE INDEX ux_card_ref ON card(card_ref);` then drop the column default once backfilled, or simpler for this lab's scale: just generate it at insert time going forward and backfill existing seeded rows in the same migration via an `UPDATE`). `CardRepository` gains `findByCardRef(String cardRef) -> Optional<Card>` alongside its existing `findByPanHash`. All Admin API responses use `card_ref`, never the internal id.
