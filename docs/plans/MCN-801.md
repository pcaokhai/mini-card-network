# MCN-801 Switch with BIN routing — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans with superpowers:test-driven-development. Worktree `../mcn-worktrees/gw-801`, branch `feat/MCN-801-switch-bin-routing`. Requires MCN-303 merged (this plan reuses `internal/isonet.Mux`/`Supervisor` and `internal/iso8583.Pack`/`Unpack` exactly as `internal/purchase.Service` already does). Independent of MCN-601/701/705 this sprint — disjoint files (`cmd/switch/`, `internal/switchrouter/`), no shared DB schema with any other Sprint 8 story.

**Goal:** `cmd/switch` sits between the gateway and the issuer, routing by a BIN table; the existing gateway re-points to the switch via config only (no gateway connection-logic code change beyond config); two issuer connections are pooled by the switch; a response may return on either connection, and the switch correlates by STAN/RRN, not connection identity.

**Architecture:** `gateway-go/cmd/switch` is a **new binary**, not a new repository directory — confirmed by listing `gateway-go/cmd/` (only `gateway` exists today) and `gateway-go/go.mod` (single module `github.com/mcn/gateway-go`, so `cmd/switch/main.go` is simply a second `main` package inside the same module, sharing `internal/isonet`, `internal/iso8583`, `internal/obs` with `cmd/gateway` — the same "one module, multiple `cmd/` binaries" layout Go projects use for a CLI-plus-daemon pair, and the layout `docs/07-delivery-plan.md`'s dependency graph (`MCN-801 → MCN-802`) already implies without needing a second Go module). A new `internal/switchrouter` package holds `Router` (`.Route(bin string) (issuerConn string, ok bool)`, a small in-memory BIN-prefix table — `map[string]string` keyed by BIN prefix length, loaded once at startup from a config file/env var, per Ruling 1) and `Switch` (the core proxy: accepts inbound connections from the gateway exactly as `issuer-jpos`'s own ISO server does today — `cmd/switch` implements the same wire protocol `internal/isonet`'s framer already speaks, since it sits on the *same* TCP link shape the gateway currently opens directly to the issuer, per `docs/02-software-architecture.md`'s network topology). `Switch` holds **two** `*isonet.Mux` instances, one per pooled issuer connection (`internal/isonet.NewMux` is reused unchanged — `Mux` already "owns the connection's single STAN counter" per its own doc comment, so pooling two of them is two independent STAN sequences, not a new counter mechanism), and a `PendingCorrelator` (a new small type — `map[correlationKey]chan response`, keyed by `(originalSTAN, rrn)` from the *inbound* gateway request, **not** by which of the two outbound `Mux` connections eventually answers — this is the literal mechanism behind AC2's "responses may return on either connection; the switch must correlate by STAN/RRN, not connection identity": whichever `Mux.Send` call returns first delivers into the same correlator entry the inbound request registered, and the switch relays that response back to the gateway over the *original inbound* connection regardless of which of the two issuer `Mux`es answered). On an inbound message, `Switch.handleInbound` parses DE 2/DE 35 (or the acquirer-supplied BIN field the fake test cards already carry, per `contracts/fixtures/cards.json`'s BIN `970436` test cards — confirm the exact DE the BIN is read from before finalizing, Task 2) through `switchrouter.Router.Route`, picks the target `Mux` (round-robin between the two pooled connections when the BIN table doesn't force a specific one — Ruling 2), sends via that `Mux.Send`, and relays the response back unchanged to the gateway's inbound connection. The gateway's own re-pointing (AC1's "via config only") is `cmd/gateway`'s existing `cfg.IssuerAddr` env var (`internal/config/config.go`) simply pointed at the switch's listen address instead of the issuer's — **zero code change** in `cmd/gateway`, confirmed because `isonet.Supervisor`/`Mux` already treat "the thing on the other end of `IssuerAddr`" as an opaque ISO 8583 peer, never assuming it's `issuer-jpos` specifically.

**Tech Stack:** Go 1.24 (new `cmd/switch` binary in the existing `gateway-go` module), existing `internal/isonet`, `internal/iso8583`, `internal/obs`.

**Spec:** `docs/06-user-stories.md` MCN-801-AC1/AC2, `docs/02-software-architecture.md` (network topology — confirm the switch's documented position between acquirer gateway and issuer before wiring), `docs/03-iso8583-interface-spec.md` §3 (DE 2/DE 35 PAN/track fields the BIN is read from), §5 (STAN/DE7 correlation — the same correlation key convention `internal/isonet.Mux`'s own doc comment already establishes, reused here at the switch's inbound/outbound boundary rather than invented fresh), `contracts/fixtures/cards.json` (the BIN `970436` test cards used in this plan's tests, per root `CLAUDE.md` §9 — no real card numbers).

## Global Constraints

- No code change to `cmd/gateway` beyond its existing `ISSUER_ADDR` config value — confirmed by this plan's own Task 4, which re-points `docker-compose.yml`'s gateway service config, not any Go source file under `internal/purchase`, `internal/isonet`, or `cmd/gateway`.
- The switch never mutates a message's business fields (amount, PAN, MAC) in transit — it is a pure router/proxy; DE 2/DE 35 (or whichever DE carries the BIN) is read, never rewritten, and the message bytes relayed to the chosen issuer connection are byte-identical to what the gateway sent (Pack/Unpack round-trip only, no field editing).
- Correlation keys (`originalSTAN`, `rrn`) are read from the inbound message exactly as `internal/isonet.Mux.Send`'s own existing `muxKey{stan, de7}` does — reusing that struct's shape (or an equivalent one) rather than inventing a third correlation convention in this codebase.
- Two issuer `Mux` connections are pooled at startup and held for the switch's lifetime — no per-request connection creation/teardown (matching `isonet.Supervisor`'s existing long-lived-connection-with-reconnect model, reused not reinvented).

## Ruling 1: BIN table is a static startup-loaded config, not a database — YAGNI for v1

A `BIN → issuer connection` table for a lab project with exactly one issuer and one BIN range (`970436`, per `contracts/fixtures/cards.json`) does not need a database-backed, hot-reloadable routing table. This plan loads the BIN table once at `cmd/switch` startup from a small YAML/env-var config (`BIN_ROUTES` env var, format `<binPrefix>:<connectionLabel>,...`, following `internal/config/config.go`'s existing `getenv`-based pattern, not a new config file format) into `switchrouter.Router`'s in-memory map. If a future story needs dynamic/hot-reloadable BIN routing, that's a new story's scope, not retrofitted here speculatively.

## Ruling 2: with only one issuer BIN range and two pooled connections to the *same* issuer, routing is BIN-keyed-with-round-robin-fallback, not BIN-to-connection-exclusive

AC1 says "routes by BIN table" and AC2 says "two issuer connections pooled... responses may return on either" — read together, this project's lab topology has one issuer behind two redundant connections (not two different issuers each owning a disjoint BIN range, which the story's own AC2 wording ("either connection") would contradict if a BIN strictly pinned one connection). This plan's `Router.Route(bin)` returns a target label from the BIN table (proving AC1's literal routing-by-BIN-table mechanism exists and is exercised, even with one entry), and `Switch.pickConnection` then round-robins between whichever pooled `Mux`es serve that target label (both of them, in this lab's one-issuer topology) — this is the smallest design that makes both AC1 (BIN table drives routing) and AC2 (either connection can answer, correlated by STAN/RRN not identity) simultaneously true and independently testable, without inventing a second issuer this project doesn't have.
