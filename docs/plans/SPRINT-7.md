# Sprint 7 — Execution Overview

> **For Claude:** This file orchestrates Sprint 7. Each story has its own plan (`MCN-50x.md`/`MCN-60x.md`/`MCN-803.md`). Execute each plan with superpowers:subagent-driven-development (or superpowers:executing-plans), one worktree per story, following root `CLAUDE.md` §4.

**Sprint goal:** Keys rotate without downtime; advanced txn groundwork. The security lane's second half lands (MCN-504's dynamic key exchange, on top of Sprint 6's MCN-501/502/503 foundation) with its own WEB visualization (MCN-505, Slice S5); in parallel, three stories pulled forward from Sprint 8's EMV/advanced-transaction epic (MCN-602, MCN-603, MCN-604 — the same "pulled forward" precedent `SPRINT-4.md` documented for MCN-302b) and one pulled forward from Sprint 8's stand-in epic (MCN-803) lay groundwork without waiting for their nominal sprint. **Duration:** 2 weeks. **Commitment:** 5 (MCN-504, split GW+ISS) + 5 (MCN-505) + 5 (MCN-602) + 5 (MCN-603) + 3 (MCN-604) + 3 (MCN-803) = 26 points. **Release:** R5, per `docs/07-delivery-plan.md` §2/§3 (Slice S5 = MCN-501+MCN-504 backend / MCN-505 frontend, flag `FF_S5_KEYS`).

**Contract-first check:** No `contracts/` PR is needed this sprint. `GET/POST /v1/keys/acquirer/rotations{,/{rotationId}}`, `KeyRotation`, and all four advanced-transaction paths (`pre-authorizations`, `{rrn}/completions`, `refunds`, `balance-inquiries`) already exist in `contracts/openapi.yaml` — confirmed by direct inspection (lines 44-99, 407-426, 789-806) before writing this file, the same "scaffolded ahead of need" pattern `SPRINT-6.md` noted for `KeyInfo`/`KeyRotation` targeting Sprint 6/7's MCN-501/504/505. This is unlike Sprint 6, which needed one small vectors-only PR (MCN-502's Task 1) — Sprint 7 needs none.

## Rulings for the whole sprint

| Ruling | Why | Cost if wrong |
| --- | --- | --- |
| Rotation-state vocabulary is fixed once, in `MCN-504-GW.md`'s Ruling 1 (restated in `MCN-504-ISS.md`'s Ruling 1): `GENERATE`/`SEND_0800_161`/`PARTNER_CONFIRM`/`ACTIVATE`, taken directly from `contracts/openapi.yaml`'s already-fixed `KeyRotation.steps[].name` enum — unlike Sprint 6's KCV Ruling, this vocabulary was never left to either lane to invent | `MCN-505.md`'s `RotationStepper` renders `steps[].name` directly as UI step labels (its own Ruling 1/2) — if GW's real emitted step names ever drifted from the contract enum, the stepper would either 404 its icon-per-step mapping or render a raw unmapped string, but since the enum is contract-fixed (not independently derived per-lane like Sprint 6's KCV convention), this risk is much lower than Sprint 6's — flagged here for completeness, not because either lane is inventing the vocabulary independently | A cosmetic stepper rendering bug in MCN-505, not a silent data-integrity issue — caught immediately in that story's own integration since the mismatch would be visually obvious, not deferred to a later sprint the way Sprint 6's KCV Ruling's cost was |
| Dual-key acceptance (both MCN-504 lanes) is implemented as a bounded-window *read* (`FindRecentlyRetired`/`findRecentlyRetired`, `MCN-504-GW.md`'s Ruling 2, mirrored in `MCN-504-ISS.md`), never a second concurrently-`ACTIVE` row — `uq_active_key`/`uq_acq_active_key`'s single-ACTIVE-row invariant from MCN-501 is never weakened | Sprint 6's `KeyStoreRepository.Activate`-retires-previous behavior is a load-bearing invariant several places already depend on (MCN-502/503's active-key lookups) — changing it to allow two ACTIVE rows would ripple into every existing active-key query, not just the new rotation code | A schema/invariant change discovered mid-sprint would force rework in MCN-502/503's already-merged code, not just this sprint's new code — the time-boxed-read design avoids that entirely |
| MCN-603's real scope this sprint is gateway-side groundwork against the fake issuer (`MCN-603.md`'s Ruling 1), not real issuer-side pre-auth/hold/completion logic (that's `MCN-601`, Sprint 8) — stated explicitly in the plan and its PR description, not left implicit | `docs/07-delivery-plan.md`'s own Sprint 7 row calls these four stories "advanced txn groundwork", and MCN-601 (the real issuer-side logic MCN-603's endpoints will eventually integrate with) is not in this sprint at all — claiming full integration this sprint would be dishonest about what's actually been proven | A tech-lead review that assumes MCN-603 proves end-to-end pre-auth/completion would be surprised at the Sprint 8 integration checkpoint when MCN-601 reveals gaps a false "done" signal from Sprint 7 papered over |
| MCN-803's velocity rules are registered via Q2 config (`MCN-803.md`'s Ruling 2), not a hardcoded `List.of(...)` in `CheckLimits.java` — the literal mechanism that makes "adding a rule needs no change to CheckLimits" true, not just a refactor that happens to look cleaner | root `CLAUDE.md` §6 rule 7 (Strategy pattern, "extend by adding, not by editing switch statements") is a Definition-of-Done-blocking rule — a Strategy refactor that still requires editing `CheckLimits.java`'s constructor to add a rule would satisfy the pattern's *shape* but not its actual intent | A code reviewer (or a future story needing a fourth rule) discovers the "config-driven" claim was cosmetic, requiring a second refactor pass later instead of getting it right in this one |
