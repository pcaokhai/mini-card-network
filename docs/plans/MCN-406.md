# MCN-406 Journey for failure scenarios — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans with superpowers:test-driven-development. Worktree `../mcn-worktrees/web-406-journey-failures`, branch `feat/MCN-406-journey-failures`. Requires MCN-307 merged (`JourneyScreen`, `StepTimeline`, `MoneyPanel`, `PlaybackControls`, `StepDetail`, all in `src/components/journey/` and `src/app/(console)/transactions/[rrn]/`). Requires MCN-401 merged gateway-side so `journey.money` can actually contain two rows (debit + refund) and `JourneyStep.kind` can actually be `"REVERSAL"`/`"WARN"` for a real transaction — until then, build and test against MSW fixtures shaped that way (same "frontend never waits for backend" rule as every prior slice).

**Goal:** The existing Journey screen (MCN-307) renders `REVERSAL`, `WARN` and `BAD` steps distinctly, the money panel shows a debit then a refund row for a reversed transaction, and a `TIMED_OUT` step shows an accelerated countdown ring during autoplay standing in for the real 30-second wait.

**Architecture:** No new screen — `StepTimeline.tsx` and `journey.css` (both already exist from MCN-307) get `data-kind`-driven styling for the two `StepKind` values the gateway didn't emit before MCN-401 (`REVERSAL`, `WARN` — `OK`/`BAD`/`INFO` already render). `MoneyPanel.tsx` already iterates `journey.money` generically (confirmed: no per-row special-casing today), so a second row (the refund) renders correctly with zero changes to that component — this plan only adds a visual distinction for a *negative-then-positive* pair (debit red-ish, refund green-ish) via a `row.delta >= 0` check already available in `MoneyPanel`'s existing JSX. `JourneyScreen.tsx`'s existing autoplay `setInterval` (`AUTOPLAY_INTERVAL_MS = 2000`) gets one addition: when the *current* step's `kind === "WARN"` and its `title` indicates a timeout (`TIMED_OUT`), a `CountdownRing.tsx` (new) renders and animates from 100% to 0% over the same 2000 ms step duration, standing in for the real 30 s server-side timer at 15× speed — purely presentational, driven by the same `currentStep`/`isPlaying` state `JourneyScreen` already owns, no new data dependency.

**Tech Stack:** Next.js App Router, TypeScript strict, existing `journey-client.ts`, CSS animations (no new library — SVG `<circle>` stroke-dashoffset countdown is a native, dependency-free technique).

**Spec:** `contracts/openapi.yaml` (`StepKind` enum incl. `REVERSAL`; `Actor` enum incl. `SAF`), `docs/06-user-stories.md` MCN-406.

## Global Constraints

- `CountdownRing` animates only `stroke-dashoffset` (an SVG presentation attribute, not a layout property) and `opacity` — compositor-friendly per `docs/rules/web/performance.md`.
- No new i18n keys duplicate existing ones — `journey.money`'s existing translation namespace is reused for the refund row's label (`row.label` already comes from the API's `Label` field, e.g. `"Refund"`, set gateway-side by `journey.moneyLabel` — MCN-406 does not hardcode a second label client-side).
- Both locales (`en.json`, `vi.json`) get any genuinely new key this story adds (the countdown ring's `aria-label` only).

## Ruling: `StepKind`/`Actor` vocabulary — must match MCN-401's gateway values exactly

MCN-401's Ruling 3 (`docs/plans/MCN-401.md`) fixes the gateway's new `journey.go` values as `Kind: "WARN"` + `Actor: "POS"` for a `REVERSAL_PENDING` step, and `Kind: "REVERSAL"` + `Actor: "SAF"` for a `REVERSED` step. This plan's MSW fixtures and `StepTimeline`'s `data-kind` styling must use exactly these two strings — confirm `contracts/openapi.yaml`'s generated TypeScript `StepKind`/`Actor` union types (`schema.ts`, regenerated by `make contracts`) already include `"REVERSAL"`/`"SAF"` before writing any component code; if the generated types are stale (generated before MCN-401 merged), regenerate first (`pnpm --filter web-next generate` or the equivalent script — confirm the exact command from `web-next/package.json`) rather than hand-widening the union type locally.

### Task 3: `CountdownRing`

**Files:** `src/components/journey/CountdownRing.tsx`, test

**Interfaces:** `CountdownRing({ durationMs, isPlaying, labelKey }: { durationMs: number; isPlaying: boolean; labelKey?: string })` — a self-contained SVG ring that animates once per mount when `isPlaying` is true, resets when `isPlaying` goes false then true again (a step re-entered during scrubbing restarts the ring rather than continuing a stale animation).

- [x] **Step 1: Write the failing test**

```tsx
import { render, screen } from "@testing-library/react";
import { describe, expect, it } from "vitest";
import { CountdownRing } from "./CountdownRing";

describe("CountdownRing", () => {
  it("renders an svg circle with a stroke-dashoffset style when playing (MCN-406-AC2)", () => {
    render(<CountdownRing durationMs={2000} isPlaying={true} />);
    const ring = screen.getByTestId("countdown-ring");
    expect(ring).toHaveAttribute("data-playing", "true");
  });

  it("pauses the ring at its current offset when isPlaying is false (MCN-406-AC2)", () => {
    render(<CountdownRing durationMs={2000} isPlaying={false} />);
    expect(screen.getByTestId("countdown-ring")).toHaveAttribute("data-playing", "false");
  });
});
```

Run: `pnpm --filter web-next test CountdownRing` → fails.

- [x] **Step 2: Implement**: an SVG `<circle>` with `stroke-dasharray`/`stroke-dashoffset` driven by a CSS `@keyframes countdown-ring { from { stroke-dashoffset: 0; } to { stroke-dashoffset: <circumference>; } }` whose `animation-duration` is set inline to `${durationMs}ms` and `animation-play-state` toggles `running`/`paused` off the `isPlaying` prop — no JS `requestAnimationFrame` loop needed for a purely visual ring (CSS animation is the lazier, equally correct choice here per the animation-performance rule preferring CSS for simple transitions).

Run: `pnpm --filter web-next test CountdownRing -v` → PASS.

- [x] **Step 3: Commit**

