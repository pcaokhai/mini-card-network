# MCN-503 PIN and MAC verification (issuer) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans with superpowers:test-driven-development. Worktree `../mcn-worktrees/iss-503`, branch `feat/MCN-503-pin-mac-verify`. Requires MCN-501 (`MCN-501-ISS.md`) merged and MCN-502's Task 1 contracts PR (`contracts/iso8583/vectors/mac/*.json`) merged — this plan's MAC verification test reads those same vector files (`MCN-502.md`'s Ruling 2: both stories build against one shared MAC contract).

**Goal:** `VerifySecurity` (currently a documented no-op at `adapter/txn/VerifySecurity.java`, wired into `40_txn_manager.xml` right after `LogAndOutbox`) becomes real: verifies the incoming request's MAC under the issuer's own ZAK copy, verifies the PIN block's PVV, tracks `card.pin_try_count`, and blocks the card on the third wrong PIN.

**Architecture:** `VerifySecurity` gains a `SecurityModule` dependency (MCN-501-ISS's `JCESecurityModule`) and a new `CardRepository`-adjacent method for `pin_try_count`/`status` updates (extends the existing card persistence rather than adding a parallel repository — confirm the exact existing `CardRepository`/`CheckCard`'s persistence class name before extending it). Two checks run in `VerifySecurity.prepare`, in this order: (1) MAC verification — recompute the Retail MAC over the received packed message (excluding DE 64/128) under the issuer's ZAK and compare to the received DE 64/128; a mismatch sets `RESPONSE_CODE = "96"` and `ABORTED`, skipping PIN verification entirely (per `docs/06` MCN-503-AC2: "bad MAC ⇒ RC 96, no posting" — no PIN check should run against a message whose integrity is already unconfirmed). (2) PVV verification — decrypts DE 52 under the issuer's TPK-equivalent (v1 has no TPK on the issuer side per `docs/03` §11's flow, "translated to ZPK by the gateway, verified via PVV by the issuer" — the issuer decrypts under **ZPK**, not TPK; confirmed by re-reading §11 before writing this plan, corrected from an initial misreading), computes the PVV (a simulated PVV algorithm — same "lab simulation" pattern `CardCrypto`'s own javadoc already establishes for ARQC, reused here rather than invented fresh) and compares to `card.pvv` (confirm this column exists in `issuer.card` before use; if it doesn't, this plan's Task 1 adds it in a migration, since PVV storage is new to this story). Wrong PVV: `RESPONSE_CODE = "55"`, `card.pin_try_count++`; third consecutive wrong PIN: `card.status = 'PIN_BLOCKED'` (the CHECK constraint already allows this value, confirmed in `V2__issuer_baseline.sql`), `RESPONSE_CODE = "75"`. DE 52 is removed from the jPOS `Context` (`ctx.remove(...)` or simply never re-added to it) immediately after this participant runs, regardless of outcome, so no later participant (`CheckLimits`, `Authorize`, `Respond`, `LogAndOutbox`'s `commit()`) can see it.

**Tech Stack:** Java 25, jPOS Q2 `TransactionParticipant`, `javax.crypto` (DES, matching MCN-502's gateway-side MAC algorithm exactly per Ruling 2 below), HikariDataSource (matching `CheckLimits`/`DeduplicateReversal`'s existing `TxnDataSource.fromConfig` pattern).

**Spec:** `docs/06-user-stories.md` MCN-503-AC1/AC2/AC3, `docs/03-iso8583-interface-spec.md` §11 (PIN block, MAC), `docs/03-iso8583-interface-spec.md` §8 RC table (`55` Incorrect PIN, `75` PIN tries exceeded, `96` System malfunction — used here for MAC failure per MCN-502's own Ruling and `docs/03` §11's "A MAC failure is answered with RC 96"), `issuer-jpos/src/main/resources/db/migration/V2__issuer_baseline.sql` (`card.pin_try_count SMALLINT`, `card.status CHECK (... 'PIN_BLOCKED' ...)` — both already exist), `adapter/txn/VerifySecurity.java` (the no-op this plan replaces), `40_txn_manager.xml` (confirms `VerifySecurity`'s exact position: after `LogAndOutbox`, before `CheckLimits`), `MCN-502.md`'s Ruling 2 (shared MAC input/output convention, `contracts/iso8583/vectors/mac/*.json`).

## Global Constraints

- DE 52 (the PIN block) is removed from `Context` immediately after `VerifySecurity.prepare` finishes — no later participant, log line, or persisted row ever sees it. This is a PCI DSS rule 2 case requiring a masking-style test with the same rigor as PAN masking, per root `CLAUDE.md` §7's Definition of Done.
- A bad MAC never triggers a PIN check — MAC verification runs first and aborts before PVV verification, per the Architecture section.
- `pin_try_count` increments only on a *verified-genuine* (MAC-good) request with a wrong PIN — a MAC failure must not count as a wrong-PIN attempt (it isn't one; the message's authenticity itself is unconfirmed).
- Money/ledger Global Constraints from root `CLAUDE.md` §6 are unchanged; a MAC or PIN failure aborts before `Authorize`, so no journal entry is posted (`Authorize` already only runs when no earlier participant set `RESPONSE_CODE`, per its own javadoc — confirmed by reading `Authorize.java`).

## Ruling 1: MAC algorithm — identical to `MCN-502.md`'s Ruling 2, restated for the implementer reading only this file

MAC input = full packed message (MTI + bitmap(s) + all present fields) excluding DE 64/128; MAC = ISO 9797-1 algorithm 3 (Retail MAC / X9.19) under the ZAK, 8 bytes. This plan's Java implementation must reproduce byte-identical MAC values to `MCN-502.md`'s Go implementation for the same input and ZAK — proven by both stories' tests reading the same `contracts/iso8583/vectors/mac/*.json` fixture (Task 1 in `MCN-502.md`; this plan's Task 2 reads the same file, never regenerates its own). If this plan's test computes a different expected MAC than the vector file states, that is a bug in *this* implementation, not a reason to add a second, ISS-only vector — the whole point of Ruling 2/Task 1 in `MCN-502.md` is one shared fixture both lanes are graded against.

## Ruling 2: PVV storage — new column, since it doesn't exist in the baseline schema

`docs/assets/baseline-schema.sql`'s `issuer.card` table (grep confirms no `pvv` column) has no PVV field — PVV storage is new to this story, unlike `key_store`/`saf_queue` which were already fully specified. This plan's Task 1 adds `card.pvv CHAR(4)` (a 4-digit Visa PIN Verification Value, the standard PVV length) via a migration that adds the column only, `NULL`-able, no seed data in the SQL migration itself — the four lab test cards in `contracts/fixtures/cards.json` (`tok_normal`/`tok_low`/`tok_blocked`/`tok_expired`, PAN prefix `970436`, all four already share `"pin": "1234"`) are seeded by `adapter/seed/SeedLoader.java`, not by hand-written `INSERT`/`UPDATE` SQL in a migration — confirmed by reading `SeedLoader.java` before writing this plan. So Task 1 also extends `SeedLoader`'s existing per-card insert with a `pvv` value computed by the same `computePvv` function `VerifySecurity` uses (Task 3), applied to each fixture's real `pan` + `"1234"` — this keeps the seeded PVV mathematically consistent with the verification algorithm instead of a hand-picked literal that could silently drift from it.
