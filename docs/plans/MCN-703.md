# MCN-703 Settlement ingestion — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans with superpowers:test-driven-development. Worktree `../mcn-worktrees/set-703`, branch `feat/MCN-703-settlement-ingestion`. Requires **both halves** of MCN-701 merged (`MCN-701-ISS.md`, `MCN-701-GW.md`) — this is a real dependency, not just wave placement: this plan's Kafka consumers read the exact topics/event shape those two plans publish. This is genuinely the **first real code** in `settlement/` — confirmed by listing `settlement/src/main/java/io/mcn/settlement/**`: every package (`config`, `application`, `domain`, `adapter/file`, `adapter/web`, `adapter/kafka`, `adapter/persistence`) currently holds only a `package-info.java` stub plus `SettlementApplicationTests`/`ArchitectureTest`/`HealthEndpointsTest` scaffolding. This plan bootstraps the domain/application/adapter classes those `package-info.java` comments already promise, inside their already-decided package layout — it does not invent a new structure.

**Goal:** Kafka consumers for both `issuer.transactions.v1` and `acquirer.transactions.v1` use the inbox pattern (dedup on `event-id`) and ack only after the DB commit; `settlement.clearing_record` holds the final state per source; an out-of-order reversal event arriving before its original is handled correctly (buffered/reconciled, not dropped or crashed on).

**Architecture:** `domain.ClearingRecord` (a pure value type per `domain/package-info.java`'s own promised shape: `source`, `businessDate`, `acquirerId`, `tid`, `stan`, `transmissionDtRaw`, `rrn`, `tranType`, `amount` (`long`), `currency`, `finalStatus`, `authCode`, `sourceTranId` — matching `settlement.clearing_record`'s already-existing baseline schema columns exactly, `docs/assets/baseline-schema.sql:514-530`; **no migration needed**, confirmed by reading the baseline schema before writing this plan — `clearing_record`/`recon_run`/`recon_break`/`net_position` all already exist). `application.IngestEvent` (a use case / port-in, per `application/package-info.java`'s promised list) is the single entry point both Kafka consumers call: given a parsed `TransactionEvent` (a DTO generated/hand-mapped from `contracts/events/transaction-event.schema.json`, in `adapter.kafka`), it upserts one `ClearingRecord` via `application.ClearingRecordRepository` (a port; `adapter.persistence.JdbcClearingRecordRepository` the outbound adapter — hexagonal, per root `CLAUDE.md` §6 rule 6: domain/application never import Spring/JDBC/Kafka types). The **inbox pattern** (AC1) is a new `settlement.inbox_event(event_id UUID PRIMARY KEY, consumed_at TIMESTAMPTZ)` table (not in the baseline schema — confirmed by grep, Task 1 adds it as this story's one real migration) that `IngestEvent` inserts into *inside the same DB transaction* as the `ClearingRecord` upsert; a Kafka consumer's manual-ack only fires after that transaction commits (`adapter.kafka`'s consumer wraps `IngestEvent.handle(event)` + `ack()` — if `handle` throws (including a duplicate `event-id` hitting `inbox_event`'s primary key, caught and treated as "already processed, skip" not an error), the consumer does not ack and Kafka redelivers, giving at-least-once-but-effectively-exactly-once processing that absorbs `MCN-701`'s own at-least-once publish gap (`MCN-701-ISS.md`/`MCN-701-GW.md`'s Ruling 2) — this is the consumer-side half of the design both those plans already promised. **Out-of-order reversal handling** (AC2): a `TransactionReversed` event whose `originalRrn` has no matching `ClearingRecord` row yet (the reversal's Kafka message overtook the original approval's, plausible since they're on different topics/partitions with no cross-topic ordering guarantee) is not dropped — `IngestEvent` inserts a `ClearingRecord` row anyway (`finalStatus='REVERSED'`, using whatever fields the reversal event itself carries — RRN, amount, tran type), and a small reconciliation-time check (added to `application`'s reconciliation use case in `MCN-704`, out of this story's scope per Ruling 2) resolves it once the original's own event arrives; **this story's own scope is limited to "does not crash and is durably recorded"** — full break-detection logic is `MCN-704`.

**Tech Stack:** Java 25, Spring Boot 3, Spring Kafka (manual ack container, `AckMode.MANUAL`), Spring Data JDBC, JUnit 5, AssertJ, Testcontainers (Postgres + Kafka), ArchUnit (already wired per `ArchitectureTest.java`).

**Spec:** `docs/06-user-stories.md` MCN-703-AC1/AC2, `docs/05-data-model.md` §"settlement" row for `clearing_record` ("Final state per transaction per source; Unique per (source, date, acq, TID, STAN, F7)"), `contracts/events/transaction-event.schema.json` (the exact event shape consumed), `docs/assets/baseline-schema.sql:514-570` (`clearing_record`, `recon_run`, `recon_break`, `net_position` — all pre-existing, this story only writes `clearing_record`), root `CLAUDE.md` §6 rule 1 (money as `long`), rule 6 (hexagonal layering — enforced by `ArchitectureTest.java`, already wired and must stay green), `MCN-701-ISS.md`/`MCN-701-GW.md` (the publishers this story consumes from — topic names `issuer.transactions.v1`/`acquirer.transactions.v1`, headers `event-id`/`event-type`/`traceparent`, RRN partition key).

## Global Constraints

- `ClearingRecord.amount` and every money field in this plan are `long` minor units — no `double`/`BigDecimal`, per root `CLAUDE.md` §6 rule 1. `domain.Money` (per `domain/package-info.java`'s promised shape) wraps `long amount, String currency` with `Math.addExact`-guarded arithmetic if this story ever sums amounts (it does not, in scope — `MCN-704` does).
- `domain` package imports nothing from `org.springframework.*`, `javax.sql.*`, `org.apache.kafka.*`, or any JDBC type — enforced by the already-wired `ArchitectureTest.java` (confirmed passing before this plan's first commit, and re-run green after every task).
- A Kafka message is acked **only after** its DB transaction (inbox insert + clearing_record upsert) commits — never before, never speculatively. A consumer crash between commit and ack causes a harmless redelivery, caught by the inbox's primary-key conflict (treated as a no-op, not an error) — this is the load-bearing correctness property AC1 requires, tested explicitly in Task 3.
- `settlement.clearing_record`'s existing unique constraint (per `docs/05-data-model.md`: "(source, date, acq, TID, STAN, F7)") is relied upon as an additional safety net against a duplicate insert slipping past the inbox check — the repository's upsert is a real `ON CONFLICT` upsert, not a blind insert, so even a theoretical inbox-table gap can't create two rows for one real-world transaction.

## Ruling 1: `settlement.inbox_event` is a new migration; `clearing_record`/`recon_run`/`recon_break`/`net_position` are not

`docs/assets/baseline-schema.sql:514-570` already defines `clearing_record`, `recon_run`, `recon_break`, and `net_position` in full — this plan writes to `clearing_record` only (the other three are `MCN-704`'s, Sprint 9's reconciliation story) and adds **zero** columns or constraints to it. The **only** new table this story's migration creates is `settlement.inbox_event(event_id UUID PRIMARY KEY, consumed_at TIMESTAMPTZ NOT NULL DEFAULT now())` — confirmed absent from the baseline schema by grep before writing this plan. This distinction matters because it would be easy to assume "first real code in settlement" means "first real migration" covers everything; it does not — most of the settlement schema was already provisioned ahead of need (the same "scaffolded ahead of need" pattern `SPRINT-6.md`/`SPRINT-7.md` noted for `KeyInfo`/`KeyRotation`), and this plan's job is to write the Java that finally uses it, plus the one genuinely missing piece (the inbox table) that no earlier sprint had a reason to anticipate.

## Ruling 2: out-of-order reversal handling in this story is "recorded correctly", not "reconciled" — that's `MCN-704`

AC2's own wording is "handled correctly (buffered/reconciled, not dropped or crashed on)" — this plan interprets "handled correctly" as: the reversal event, however it arrives, always produces exactly one durable `ClearingRecord` row with `finalStatus='REVERSED'` and never throws an unhandled exception regardless of whether the original transaction's row already exists. It does **not** implement cross-event business validation (e.g. "does this reversal's amount match its original's amount") — that comparison needs both rows to exist and is exactly what `MCN-704`'s `reconcile()` pure function (its own AC1, "covering all `BreakType`s with table-driven tests") is scoped to do next sprint. Building partial reconciliation logic here would duplicate `MCN-704`'s own design and risk diverging from its `BreakType` taxonomy before that taxonomy is even written — YAGNI.
