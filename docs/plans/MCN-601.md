> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans with superpowers:test-driven-development. Worktree `../mcn-worktrees/iss-601`, branch `feat/MCN-601-preauth-completion`. Requires MCN-402 merged (this plan's `HoldExpiryJob` follows the same scheduled-job shape reversal/SAF-adjacent code already established) and reuses `issuer.auth_hold` — already in the baseline schema (`docs/assets/baseline-schema.sql:199-218`, `issuer-jpos/src/main/resources/db/migration/V2__issuer_baseline.sql:154-172`) but with **no repository or participant code written against it yet** (confirmed by grep — this plan is the first to touch it). This is the last piece of **Slice S6** (`docs/07-delivery-plan.md` §2): MCN-602/603/604 are already merged; this story flips `FF_S6_ADV_TXN` on once it lands (see Task 6's exit note).

**Goal:** 0100 with DE 25=`06` creates an `ACTIVE` auth_hold (available balance decreases, the ledger does not); a 0220 completion ≤ the hold amount posts the journal for the final amount, releases the remainder, answers 0230; a completion > the hold amount is recorded and flagged for reconciliation (v1: not auto-resolved); a `HoldExpiryJob` releases expired holds and emits `HoldExpired` to the outbox.

**Architecture:** Two new jPOS `TransactionParticipant`s follow the exact shape of `Authorize`/`CheckLimits` (`adapter/txn/`, `HikariDataSource` built per-instance in `setConfiguration`, own connection, own transaction — per `Authorize.java`'s documented finding that jPOS 3.0.1 never shares a JDBC `Connection` across participants): `CreateHold` (0100 + DE 25=`06`, wired into `40_txn_manager.xml` in place of `Authorize` for the pre-auth processing-code branch — see Ruling 1 for how the chain distinguishes pre-auth from purchase) and `CompleteHold` (0220, a new completion-specific transaction manager chain, `60_completion_txn_manager.xml`, since 0220 is an advice, not a request/response MTI, and jPOS routes advices through a different `ISORequestListener`/queue than 0100/0200 — confirmed by reading `30_iso_server.xml`'s existing MTI-to-queue mapping before adding a new one). `CreateHold` inserts an `auth_hold` row (`status='ACTIVE'`, `remaining_amount = amount`) via a new `AuthHoldRepository` (mirrors `TranLogRepository`'s shape) — no `journal_entry` row (holds are not ledger entries per AC1 and `docs/05-data-model.md`'s comment "One per transaction; partial index on ACTIVE expiry"); "available balance decreases" is computed, not stored — `AuthHoldRepository.sumActiveHoldAmounts(accountId)` is added to whatever balance-check `CheckLimits`/`Authorize` already run, so a purchase against an account with an open hold sees a reduced available balance without a new column on `account`. `CompleteHold` looks up the `auth_hold` row by `tran_id`/RRN reference (DE 37 in the 0220 must carry the pre-auth's RRN, per `docs/03-iso8583-interface-spec.md`'s Notes **C8** "completion references the pre-auth"), and branches on `completionAmount <= remainingAmount`: within-hold posts one `journal_entry` (entry_type `COMPLETION`) for the completion amount, sets `auth_hold.status='COMPLETED'`, `remaining_amount=0`, answers 0230 RC `00`; over-hold (AC2's "flagged for reconciliation, v1") posts the journal for `remainingAmount` only (the hold's own ceiling — never journal more than was actually held), sets `auth_hold.status='COMPLETED'` with `remaining_amount=0`, and inserts one `outbox_event` row `event_type='completion.over_hold'` carrying `{holdId, remainingAmount, completionAmount}` (no new column, no new state — the existing `outbox_event` JSONB payload is the flag; MCN-703/704's settlement break detection in Sprint 9 already reconciles from outbox-derived events, so this v1 "flagged" behavior needs no new machinery, per YAGNI). `HoldExpiryJob` is a Q2 `TimerTask`/`org.jpos.q2.QBean`-style scheduled component (grep confirms no existing scheduled-job precedent in this codebase other than the SAF worker's own polling loop in `gateway-go`; the issuer side's nearest analogue is `AuthHoldRepository.releaseExpired(now)` run on a fixed interval, wired the same way `40_txn_manager.xml`'s participants are wired — a new `70_hold_expiry_job.xml` Q2 deploy descriptor with a `<mbean>` polling every 60s, per `docs/03` §9's general "timers are named constants, not literals" convention) — each release: `UPDATE auth_hold SET status='EXPIRED' WHERE status='ACTIVE' AND expires_at < now()` (using `ix_hold_expiry`'s existing partial index), one `outbox_event` row per released hold, `event_type='HoldExpired'` (matching `contracts/events/transaction-event.schema.json`'s `eventType` enum exactly — already lists `HoldCreated`/`HoldCompleted`/`HoldExpired`, confirmed no schema change needed).

**Tech Stack:** Java 25, jPOS Q2 (`TransactionParticipant`, `QBean`/`TimerTask` scheduling), Hikari/JDBC, JUnit 5, AssertJ, Mockito.

**Spec:** `docs/06-user-stories.md` MCN-601-AC1/AC2/AC3, `docs/03-iso8583-interface-spec.md` §6/§7.3 (`000000` + DE 25=`06` pre-authorization, MTI `0100`), §7.4 (0220 completion is an advice — SAF/repeat-until-0x30, never declined), Notes **C8** ("completion references the pre-auth"), `docs/05-data-model.md` §"issuer" row for `auth_hold` ("One per transaction; partial index on ACTIVE expiry"), `contracts/events/transaction-event.schema.json` (`HoldCreated`/`HoldCompleted`/`HoldExpired` eventTypes, already present — no contract change), root `CLAUDE.md` §6 rule 1 (money as `long` minor units) and rule 5 (double-entry ledger: holds are not journal entries, only completions are).

## Global Constraints

- `auth_hold.amount`, `remaining_amount`, and every `journal_entry` amount this plan posts are `long` minor units — never `double`/`BigDecimal`, per root `CLAUDE.md` §6 rule 1.
- A hold is never itself a `journal_entry` row (AC1: "available decreases, ledger does not") — the only `journal_entry` rows this plan creates come from `CompleteHold`, and only for the amount actually completed (≤ the hold's original amount).
- Every state-changing write (`CreateHold`'s insert, `CompleteHold`'s update+journal, `HoldExpiryJob`'s expiry) happens inside one explicit JDBC transaction per participant/job run, on one connection it owns and closes itself — mirrors `Authorize.java`'s documented finding, not re-derived per participant.
- `uq_hold_tran` (one `auth_hold` row per `(tran_id, tran_business_date)`) is never weakened; `CreateHold` relies on this constraint to make a retried/duplicate 0100 pre-auth a no-op insert failure caught the same way `Deduplicate` already catches other duplicate submissions.

## Ruling 1: pre-auth is routed by processing code + DE 25, not a new MTI or new queue

`docs/03` §7.3's table shows pre-authorization as MTI `0100` (the same request MTI as sign-on/network-management messages use `0800`, but `0100`/`0200` share the authorization queue per `30_iso_server.xml`) with DE 3=`000000` and DE 25=`06` distinguishing it from a plain purchase (DE 25=`00`). `ParseAndValidate` (the chain's first participant, unchanged) already parses DE 25 into the `Context` for every 0100/0200 message — confirmed by reading `ParseAndValidate.java` before this plan assumed it. `40_txn_manager.xml`'s existing chain is **not** duplicated wholesale for pre-auth: `ParseAndValidate → Deduplicate → CheckCard → LogAndOutbox → VerifyEmv → VerifySecurity → CheckLimits` all run identically for a pre-auth as for a purchase (the same fraud/limit/security checks must apply to an amount that will become an active hold). Only the final participant differs: this plan adds a **branching** step — `AuthorizeOrHold` is **not** a new class; instead, `CreateHold` is inserted into the chain immediately before `Authorize` and checks DE 25 itself: DE 25=`06` → runs its own hold-creation logic and returns `PREPARED` early (short-circuiting `Authorize`, which never runs for a pre-auth); DE 25 anything else → returns `PREPARED` immediately as a no-op, letting `Authorize` run unchanged. This is the same "no-op unless the specific business code matches" pattern `MCN-504-ISS.md`'s `ReceiveKeyChange` established for DE 70=`161` inside the 0800 chain — confirmed as an established precedent in this codebase, not invented fresh here.

## Ruling 2: over-hold completion is "flagged", not auto-adjusted, per AC2's own v1 scope

AC2 says an over-hold completion is "recorded and flagged for reconciliation (v1)" — explicitly not resolved automatically. This plan posts the journal for `remainingAmount` only (never more than the hold actually reserved — posting the full requested completion amount would let a completion silently create money the hold never backed) and writes one `outbox_event` flagging the discrepancy, rather than building new UI, a new table, or an auto-resolution rule this sprint. MCN-703/704 (Sprint 9's settlement ingestion and reconciliation) already consume `outbox_event`-derived Kafka events and already have a `BreakType` enum (`docs/06-user-stories.md` MCN-704-AC1) general enough to classify this discrepancy later — this plan does not anticipate or special-case that classification, per YAGNI; it only guarantees the fact is durably recorded and observable in the outbox.
