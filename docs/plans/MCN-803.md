# MCN-803 Velocity rules — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans with superpowers:test-driven-development. Worktree `../mcn-worktrees/iss-803`, branch `feat/MCN-803-velocity-rules`. Requires MCN-302 merged. Independent of MCN-504/505/602/603/604 — touches `adapter/txn/CheckLimits.java` and a new `adapter/persistence/VelocityCounterRepository.java`, disjoint from every other Sprint 7 story's files.

**Goal:** Count and amount limits per card per day are enforced using `velocity_counter` (already defined in the baseline schema, `docs/assets/baseline-schema.sql:128-136`, currently unused by any repository): exceeding a count limit answers RC `65`, exceeding an amount limit answers RC `61`. Rules are strategies registered in config; adding a new rule needs no change to `CheckLimits`.

**Architecture:** `CheckLimits.java` (existing, `adapter/txn/`) currently checks `card_limit` ceilings inline with three duplicated `if` blocks (PER_TXN amount, DAILY count, DAILY amount) — a literal violation of root `CLAUDE.md` §6 rule 7 ("extend by adding, not by editing switch statements") for exactly the shape MCN-803's own AC2 calls out ("adding a rule needs no change to CheckLimits"). This plan introduces a `VelocityRule` interface (`application/VelocityRule.java`, new port) with one implementation per rule kind — `PerTransactionAmountRule`, `DailyCountRule`, `DailyAmountRule` (the Strategy pattern root `CLAUDE.md` §6 rule 7 names for exactly this problem: "extend by adding [a new strategy], not by editing switch statements"). `CheckLimits` is refactored to hold `List<VelocityRule>` (injected, not hardcoded) and loop over them, stopping at the first that declines — the existing inline logic's three branches become the first three registered rules, moved out of `CheckLimits`'s own body entirely. `VelocityCounterRepository` (new, `adapter/persistence/`, same shape as `CardLimitRepository`) reads/writes `velocity_counter`, which `CardLimitRepository.countToday` currently approximates via a `tran_log` count query (grep confirms this in Task 1) — this plan switches the daily-count/amount check to the real `velocity_counter` fast-counter table the schema already reserves for this purpose (its own comment: "Bộ đếm cập nhật trong cùng DB transaction với authorize (nhanh hơn SUM trên tran_log)" — "counter updated in the same DB transaction as authorize, faster than SUM over tran_log"), updated atomically in the same transaction as `Authorize`.

**Tech Stack:** Java 25, jPOS Q2, JUnit 5, AssertJ.

**Spec:** `docs/06-user-stories.md` MCN-803-AC1/AC2, `docs/assets/baseline-schema.sql:128-136` (`velocity_counter` exact DDL, transcribed below), `docs/03-iso8583-interface-spec.md` §8 ("61 | Exceeds amount limit | Daily or per-transaction limit", "65 | Exceeds frequency limit | Velocity count"), root `CLAUDE.md` §6 rule 7 (SOLID/Strategy — "extend by adding (new participant, new strategy), not by editing switch statements").

## Global Constraints

- `VelocityRule` implementations are stateless, constructor-injected with only the repository/config they need — no rule reads another rule's intermediate state (each evaluates independently against `velocity_counter`/`card_limit`, matching the Strategy pattern's isolation requirement).
- Adding a fourth rule (e.g. a future MONTHLY rule) means: write a new `VelocityRule` implementation class + one new config registration line — zero changes to `CheckLimits.java`'s body. This plan's Task 4 proves it with a test that adds a throwaway fourth rule and asserts `CheckLimits` needs no modification to pick it up.
- `velocity_counter` updates happen in the same DB transaction as `Authorize`'s ledger posting (per the schema's own comment) — a declined transaction (RC 61/65) must **not** increment the counter (only a transaction that actually posts should count against tomorrow's/today's velocity).
- Money (`txn_amount BIGINT`) stays `long` throughout — no floating point, per root `CLAUDE.md` §6 rule 1 (unchanged, restated because this plan touches amount comparisons).

## Ruling 1: `VelocityRule` Strategy replaces `CheckLimits`'s three inline `if` blocks — not a new parallel system

`CheckLimits.java`'s current body (read in full before writing this plan) has three near-identical `if` blocks differing only in period/field checked — exactly the "switch statement smell" root `CLAUDE.md` §6 rule 7 names. This plan does not add velocity rules *alongside* the existing inline checks; it **replaces** them, moving each existing branch's logic into its own `VelocityRule` implementation one-for-one (`PerTransactionAmountRule` ← the `PER_TXN`/`maxAmount` branch, `DailyCountRule` ← the `DAILY`/`maxCount` branch using the new `velocity_counter`-backed count instead of `CardLimitRepository.countToday`'s `tran_log` scan, `DailyAmountRule` ← the `DAILY`/`maxAmount` branch). `CheckLimits`'s post-refactor body is a single loop: `for (VelocityRule rule : rules) { Optional<String> declineRc = rule.evaluate(cardId, amount); if (declineRc.isPresent()) { ctx.put(RESPONSE_CODE, declineRc.get()); return ABORTED; } }` — no rule-kind-specific branching left in `CheckLimits` itself.

## Ruling 2: rule registration is config-driven (a Q2 `.xml`/`.cfg` list), not a hardcoded Java array

"Rules are strategies registered in config" (MCN-803-AC2's own wording) means the *set and order* of active rules is a Q2 configuration concern, not a compiled-in `List.of(...)` inside `CheckLimits`'s constructor. `CheckLimits.setConfiguration` (the existing `Configurable` entrypoint every participant already implements) reads a new config property, `rules` (a comma-separated list of fully-qualified `VelocityRule` implementation class names, mirroring how jPOS's own `QFactory` already instantiates participants by class name from XML — the same reflection-based construction convention, applied one level down to rules instead of participants), and reflectively instantiates each one via `Class.forName(name).getDeclaredConstructor(...).newInstance(...)`. This is the mechanism that makes "adding a rule needs no code change to `CheckLimits`" literally true — a new rule class plus one new line in a deploy `.xml`/`.cfg` file, no recompiled `CheckLimits.java`.
