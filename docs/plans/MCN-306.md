Does **not** wait for MCN-304 (GW, Sprint 4) — builds against MSW mocks from `contracts/openapi.yaml`'s `/v1/metrics/overview` and the `transaction.created`/`transaction.updated` WS events already defined in `contracts/ws-events.schema.json`. **Goal:** An overview screen: 4 KPI cards (transactions today, approval rate, p99 latency, ledger-matches indicator), a 60-minute throughput bar chart, a decline-reasons breakdown, a system health list, a cutover countdown, and a live transaction feed that slides in new rows from WS events with batched updates under load.

**Architecture:** `web-next/src/app/(console)/overview/` — `OverviewScreen.tsx` (container: `useQuery` for `GET /v1/metrics/overview`, refetched on a timer since KPIs are inherently point-in-time snapshots, not something to over-engineer with WS push this sprint — YAGNI, `network.*` events already prove the WS pattern works and this screen's own live piece is the feed, not the KPIs), `KpiCards.tsx`, `ThroughputChart.tsx` (a real data-viz component per `rules/web/design-quality.md`'s point 10, not a generic bar div — use CSS-only bars with `transform: scaleY()` for compositor-friendly height animation, avoiding a heavy charting library for 60 data points, per YAGNI/ponytail's "stdlib/native before a dependency" ladder), `DeclineReasonsBreakdown.tsx`, `SystemHealthList.tsx`, `CutoverCountdown.tsx`, `LiveFeed.tsx` (subscribes to `transaction.created`/`transaction.updated` via the existing WS hub client, batches incoming events every 500ms once the rate exceeds 5/s per AC2, caps at 30 rows).

**Tech Stack:** Next.js App Router, TanStack Query, MSW, Vitest + Testing Library, Storybook, `next-intl`, native `WebSocket` (or whatever thin WS client wrapper MCN-004/MCN-205 already established — check before adding a new one).

**Spec:** `contracts/openapi.yaml` (`Overview` schema), `contracts/ws-events.schema.json` (`transaction.created`/`transaction.updated` → `TransactionSummary`), `docs/06-user-stories.md` MCN-306, `rules/web/design-quality.md`, `rules/web/performance.md` (batching under load is itself a performance/CWV concern — unbatched high-frequency DOM updates would blow the INP budget).

## Global Constraints

- Money in `Overview`/`TransactionSummary` stays typed as the `Money` schema (`{amount, currency}`); never format/derive currency math client-side beyond display formatting.
- Feed batching: below 5 events/s, render immediately; at or above 5 events/s, coalesce into one DOM update per 500ms window (AC2's exact numbers — don't invent a different threshold).
- Max 30 rows in the feed at any time (AC2) — oldest rows drop off, not just visually truncate (unmount them, don't just `overflow: hidden` a growing list, for real memory/DOM-node hygiene).

## Ruling: no `useWsEvents` hook exists yet — this story is the first real consumer

MCN-205 (Sprint 2) flagged that no shared WS-consuming hook exists in `web-next/`; MCN-204 (Sprint 2, GW) built the hub and its wire format but nothing on the frontend consumes it live yet. This story is the first to actually need one (the live feed genuinely needs push, unlike MCN-205's status pill which tolerates polling). Build a small shared `useWsEvents(eventTypes: string[], onEvent: (event) => void)` hook in `src/shared/ws/useWsEvents.ts` this story — not a bigger abstraction than needed (a single hook, reconnect-with-backoff reusing whatever pattern `docs/02-software-architecture.md` or MCN-202's gateway-side backoff already documents conceptually, just translated to the browser's `WebSocket` API) — and note in the PR that MCN-205's screen can be migrated from polling to this hook as a fast-follow, though that migration itself is out of this story's scope (don't touch MCN-205's files here — a separate, later, single-file change).

- [ ] **Step 2: Implement**

```ts
import { useEffect, useRef } from 'react'

interface WsEnvelope {
  id: string
  type: string
  occurredAt: string
  data: unknown
}

export function useWsEvents(eventTypes: string[], onEvent: (event: WsEnvelope) => void) {
  const onEventRef = useRef(onEvent)
  onEventRef.current = onEvent

  useEffect(() => {
    let socket: WebSocket | null = null
    let closed = false
    let attempt = 0

    function connect() {
      if (closed) return
      const url = `${location.protocol === 'https:' ? 'wss' : 'ws'}://${location.host}/v1/stream`
      socket = new WebSocket(url)
      socket.onmessage = (event) => {
        const envelope: WsEnvelope = JSON.parse(event.data)
        if (eventTypes.includes(envelope.type)) onEventRef.current(envelope)
      }
      socket.onclose = () => {
        if (closed) return
        const delay = Math.min(30_000, 1000 * 2 ** attempt)
        attempt += 1
        setTimeout(connect, delay)
      }
    }
    connect()

    return () => {
      closed = true
      socket?.close()
    }
  }, [eventTypes.join(',')])
}
```

Check: the reconnect backoff here deliberately mirrors MCN-202's gateway-side full-jitter shape conceptually (1s base, 30s cap) but without the jitter randomization for simplicity in the browser — since this is a UI convenience reconnect, not a link-integrity-critical path, plain exponential backoff is sufficient (YAGNI on porting the exact jitter algorithm client-side).
