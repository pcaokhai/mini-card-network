# MCN-602 EMV field 55 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans with superpowers:test-driven-development. Worktree `../mcn-worktrees/iss-602`, branch `feat/MCN-602-emv-field55`. Requires MCN-302 merged (this plan adds a new participant to the existing purchase transaction chain, alongside `CheckCard`/`CheckLimits`/`VerifySecurity`). Independent of MCN-504/505/603/803 — disjoint files (`adapter/crypto/`, `adapter/txn/`), no shared migration.

**Goal:** Chip transactions carry EMV data in DE 55; the issuer parses its TLV tags, rejects malformed TLV with RC `30`, simulates ARQC verification (keyed HMAC, matching the "lab simulation" convention `docs/03` §11 already documents for ARQC and `PvvCalculator` already establishes in code for PVV), rejects a non-increasing ATC (replay) with RC `05`, and returns a simulated ARPC in tag `91` on a `00`/`10` response.

**Architecture:** A new `EmvTlvParser` (`adapter/crypto/`, pure parsing logic, no I/O — a small value-type parser, not a participant) decodes DE 55's hex TLV into a `Map<String, byte[]>` keyed by tag, recognizing the seven tags `docs/03` §11 lists (`9F26` ARQC, `9F27` CID, `9F10` IAD, `9F36` ATC, `9F37` unpredictable number, `95` TVR, `9A` date, `9C` type, `5F2A` currency — nine tags total, matching the spec's own list exactly). A new `ArqcSimulator` (`adapter/crypto/`, same "simulated in the lab" javadoc convention as `PvvCalculator`: a keyed HMAC over the transaction data under a fixed, documented, non-secret simulator key — never a real EMV cryptographic key derivation) verifies the ARQC in tag `9F26` and computes the ARPC returned in tag `91`. A new `VerifyEmv` `TransactionParticipant` (`adapter/txn/`, same shape as `VerifySecurity`/`CheckLimits`) runs after `CheckCard` and before `VerifySecurity` in the purchase chain (confirmed against the real participant ordering in `docs/dist/deploy` — EMV validation belongs before PIN/MAC checks since a malformed TLV is a format error independent of PIN/MAC, matching RC `30`'s "Packager/validation failure" framing in `docs/03` §8): parses DE 55 only when present (chip entry mode), rejects malformed TLV with RC `30`, compares the parsed ATC (`9F36`) against `card.emv_last_atc` (already a column per `docs/assets/baseline-schema.sql:110`, "ATC gần nhất, chống replay cryptogram"), rejects a non-increasing ATC with RC `05`, verifies the ARQC via `ArqcSimulator`, and on a `00`/`10` outcome sets tag `91` (ARPC) in the outgoing DE 55 before `Respond` packs the 0210.

**Tech Stack:** Java 25, `javax.crypto` (`HmacSHA256`, matching `PvvCalculator`'s algorithm choice), JUnit 5, AssertJ.

**Spec:** `docs/06-user-stories.md` MCN-602-AC1/AC2/AC3, `docs/03-iso8583-interface-spec.md` §11 ("EMV (DE 55): TLV; v1 recognizes tags 9F26 (ARQC), 9F27 (CID), 9F10 (IAD), 9F36 (ATC), 9F37 (unpredictable number), 95 (TVR), 9A (date), 9C (type), 5F2A (currency). ARQC verification is simulated with a keyed HMAC in the lab; ARPC returned in tag 91."), `docs/03` §8's RC `05`/`30` rows ("05 | Do not honor | Generic decline, velocity rule (v1 fallback)" — reused here for ATC replay, since no more specific RC exists for this condition; "30 | Format error | Packager/validation failure"), `docs/assets/baseline-schema.sql:110` (`card.emv_last_atc INTEGER`), `PvvCalculator.java` (the "simulated in the lab" javadoc convention this plan's `ArqcSimulator` follows verbatim).

## Global Constraints

- `EmvTlvParser` never throws on well-formed-but-unrecognized tags (ignore and skip, per TLV's own self-describing length — only a length/structure violation is malformed); malformed structure (truncated length, length exceeding remaining bytes) is the only condition that produces RC `30`.
- `ArqcSimulator`'s key is a fixed, documented, non-secret simulator key (same class of value as `PvvCalculator.SIMULATOR_PVK`) — never wired to any real key-management path, never read from `LMK_TEST_VALUE_HEX`/ZAK/ZPK (those are real security primitives from MCN-501/502/503; ARQC simulation is explicitly a teaching illustration, matching `docs/03` §11's own "simulated" wording).
- `card.emv_last_atc` updates only on a successfully-verified ARQC with a strictly-increasing ATC — a rejected (RC 05/30) transaction never advances the stored ATC (otherwise a replayed lower ATC could accidentally "catch up" past a skipped legitimate transaction).
- Money and all other root `CLAUDE.md` §6 Global Constraints unchanged; this story adds no new money field.

## Ruling 1: RC `05` for ATC replay, not a new response code

`docs/03` §8 has no RC dedicated to "cryptogram/ATC replay" — the closest existing row is `05 | Do not honor | Generic decline, velocity rule (v1 fallback)`, already documented as a v1 fallback bucket. `docs/06-user-stories.md`'s MCN-602-AC2 ("replay ⇒ RC 05") confirms this is the story's own explicit choice, not left to this plan to invent — `VerifyEmv` reuses RC `05` verbatim, no new code added to `docs/03`'s RC table (a table change would be a `contracts`/doc-only PR outside this plan's scope, and none is needed since the value is already spec'd).

## Ruling 2: TLV tag set is fixed to the nine tags `docs/03` §11 lists — no speculative EMV coverage

Real EMV TLV has dozens of tags; this plan's `EmvTlvParser` only special-cases the nine tags the spec names (`9F26`, `9F27`, `9F10`, `9F36`, `9F37`, `95`, `9A`, `9C`, `5F2A`) for typed extraction — any other well-formed tag is parsed structurally (into the raw map) but never given a named accessor, per YAGNI (this is a teaching lab, not a full EMV kernel; `docs/06`'s AC1 says "tags listed in ISO spec §11", not "every EMV tag").

Tag keys are uppercase hex strings (`"9F26"`, `"95"`, etc.), matching DE 55's own hex-TLV convention (`contracts/openapi.yaml`'s `emvData` field: `'^([0-9A-F]{2})*$'`).

```java
package io.mcn.issuer.adapter.crypto;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

import java.util.HexFormat;
import java.util.Map;
import org.junit.jupiter.api.Test;

class EmvTlvParserTest {

  @Test
  void should_parse_two_single_byte_length_tags__MCN_602_AC1() {
    // 9F36 (ATC) len 02 value 0001, 95 (TVR) len 05 value 0000000000
    byte[] tlv = HexFormat.of().parseHex("9F3602000195050000000000");

    Map<String, byte[]> tags = EmvTlvParser.parse(tlv);

    assertThat(tags).containsKey("9F36");
    assertThat(tags.get("9F36")).isEqualTo(HexFormat.of().parseHex("0001"));
    assertThat(tags).containsKey("95");
  }

  @Test
  void should_reject_truncated_length__MCN_602_AC1() {
    byte[] tlv = HexFormat.of().parseHex("9F3605"); // declares length 5, no value bytes follow

    assertThatThrownBy(() -> EmvTlvParser.parse(tlv))
        .isInstanceOf(EmvTlvParser.MalformedTlvException.class);
  }

  @Test
  void should_skip_unrecognized_but_well_formed_tags__MCN_602_AC1() {
    // DF01 (unrecognized) len 01 value FF, then 9C (type) len 01 value 00
    byte[] tlv = HexFormat.of().parseHex("DF0101FF9C0100");

    Map<String, byte[]> tags = EmvTlvParser.parse(tlv);

    assertThat(tags).containsKey("9C");
    assertThat(tags).containsKey("DF01"); // parsed structurally even though it has no named accessor
  }
}
```

### Task 4: `VerifyEmv` participant — parse, replay-guard, ARQC verify, ARPC set (AC1, AC2, AC3)

**Files:** `adapter/txn/VerifyEmv.java`, test

**Interfaces:** `VerifyEmv(EmvTlvParser parser, ArqcSimulator arqcSimulator, CardRepository cardRepository)`; jPOS `TransactionParticipant.prepare(long, Serializable)`.
