# MCN-603 Advanced transaction endpoints (gateway) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans with superpowers:test-driven-development. Worktree `../mcn-worktrees/gw-603`, branch `feat/MCN-603-adv-txn-endpoints`. Requires MCN-303 merged (this plan follows `purchase.Service.sendPurchase`'s established pattern for a second transaction family). Slice **S6** — this plan builds gateway-side groundwork only; the full S6 slice (real issuer-side pre-auth/completion/hold logic, MCN-601) doesn't land until Sprint 8, so this story's endpoints are honest about what they can prove this sprint (see Ruling 1). Independent of MCN-504/505/602/803 — disjoint files (`internal/advtxn/`, `internal/api/`).

**Goal:** `POST /v1/transactions/pre-authorizations`, `POST /v1/transactions/{rrn}/completions`, `POST /v1/transactions/refunds`, `POST /v1/transactions/balance-inquiries` per `contracts/openapi.yaml`'s already-scaffolded paths: pre-auth sends 0100 with DE 25=`06`; completion sends 0220 referencing the original RRN; refund sends 0200 with DE 3=`200000`; balance inquiry sends 0200 with DE 3=`310000` and returns `balance` from DE 54. Partial approval (RC `10`) returns `approvedAmount` distinct from the requested amount.

**Architecture:** A new `internal/advtxn` package (mirroring `internal/purchase`'s shape — `Service`, `Transaction`, `*Request` types — kept separate rather than folded into `purchase.Service` because the four new flows use different MTIs/processing codes and a completion's request shape (references an existing RRN, no card-present data) genuinely differs from a purchase's, so a shared struct would need optional/nullable fields for every flow — YAGNI says split now rather than grow one struct to serve five shapes). `advtxn.Service.CreatePreAuth`/`CreateCompletion`/`CreateRefund`/`CreateBalanceInquiry` each build and send one ISO message via the same `mux`/`codec`/MAC-wrapping pipeline `purchase.Service.sendPurchase` already established (MCN-502's MAC step is reused unconditionally — every message this plan sends goes through the same `hsm.ComputeMAC` wrapping, no new path that skips it), and reuse `purchase.Service`'s already-wired `tranLog`, `idempotency`, `hub` (WS) dependencies rather than re-deriving them (constructor takes the same dependency shapes as `purchase.NewService`, confirmed by reading its current signature before writing `advtxn.NewService`'s). DE 3 processing codes: pre-auth `000000` + DE 25=`06` on MTI `0100` (`docs/03` §6/§7.3); completion MTI `0220` (referencing the pre-auth's RRN in DE 37, per `docs/03` §"C8 completion references the pre-auth"); refund DE 3=`200000` on MTI `0200`; balance inquiry DE 3=`310000` on MTI `0200`, response `balance` mapped from DE 54. A partial approval (issuer or fake-issuer answers RC `10` with DE 4 less than the requested amount, per `docs/03`'s "C1 partial approval returns the approved amount in DE 4 with RC 10") sets `Transaction.ApprovedAmount` distinct from `Transaction.Amount` in the JSON response, matching `contracts/openapi.yaml`'s `Transaction.approvedAmount` field exactly.

**Tech Stack:** Go 1.24, existing `internal/purchase`, `internal/mux`, `internal/iso8583`, `internal/hsm`, chi.

**Spec:** `docs/06-user-stories.md` MCN-603-AC1/AC2, `contracts/openapi.yaml:44-99` (the four already-scaffolded paths and `Transaction`/`PurchaseRequest`/`Money` schemas), `docs/03-iso8583-interface-spec.md` §6 (processing codes table), §7.3 ("000000 + DE 25 06 | Pre-authorization (with MTI 0100)"), the DE table's footnotes (C1 partial approval, C6 balance inquiry DE 3=`31xxxx`, C8 completion references the pre-auth), root `CLAUDE.md` §6 rule 1 (money as integer minor units — `approvedAmount`/`balance` are both `Money{amount int64, currency string}`, never a float).

## Global Constraints

- `approvedAmount` and `balance` are both `int64` minor units through the whole pipeline (DE 4/DE 54 parse → `Money` struct → JSON) — no floating-point conversion anywhere, per root `CLAUDE.md` §6 rule 1.
- Every outgoing message from `advtxn.Service` is MAC'd via `hsm.ComputeMAC` before send and every incoming response's MAC is verified before its fields are trusted — no new path bypasses MCN-502's MAC wrapping.
- `Idempotency-Key` is required on all four new endpoints, matching `contracts/openapi.yaml`'s `IdempotencyKey` parameter and `purchases.go`'s existing enforcement pattern.
- No new dependency: `advtxn.Service` reuses `internal/mux`, `internal/iso8583`, `internal/hsm`, `internal/store` exactly as `purchase.Service` does — no second codec or transport.

## Ruling 1: this sprint proves these endpoints against the fake issuer, not real hold/completion logic — flagged honestly, not silently

`MCN-601` (real issuer-side pre-authorization/completion logic: `auth_hold` table writes, hold expiry, partial-completion accounting) is Sprint 8's story, not this sprint's — `docs/07-delivery-plan.md`'s own Sprint 7 row describes MCN-602/603/804 as "advanced txn groundwork" pulled forward, the same precedent `SPRINT-4.md` documented for MCN-302b. This plan's integration tests therefore run against `gateway-go/internal/chaos/fakeissuer` (already built for MCN-407's chaos suite — reused here, not a new fake), configured to answer 0100/0220 with a scripted RC `00`/`10` and DE 4/DE 54 values, **not** against a real `issuer-jpos` pre-auth participant chain (which doesn't exist until Sprint 8). This plan's own AC (gateway sends the right MTI/DE 3/DE 25 combination, parses `approvedAmount`/`balance` correctly, returns the right JSON shape) is fully provable against the fake issuer; the AC this plan does **not** claim — "a real hold is created and later completed end-to-end at the issuer" — is explicitly out of scope and re-tested for real in Sprint 8's `MCN-601` plan once that participant chain exists. `make up && make e2e`'s Sprint 7 integration checkpoint therefore only exercises these endpoints against the fake issuer or a fixture-driven stand-in — not the real `issuer-jpos` — and this is stated in this plan's own exit criteria rather than left implicit.

## Ruling 2: `advtxn` is a new package, not folded into `purchase.Service`

`purchase.Service.sendPurchase` already handles one request shape (`PurchaseRequest` — card-present data + amount). Completion's request has no card-present data at all (it references an existing RRN); balance inquiry has no amount. Bolting all five flows onto one `Service`/`Request` type would mean every flow-specific field becomes optional on every other flow's request — the same "one struct serves five shapes" antipattern YAGNI warns against. `advtxn.Service` is a sibling package with its own `Request`/`Transaction` types per flow, reusing `purchase.Service`'s already-proven dependencies (mux, hsm, tranLog, idempotency, hub) via the same constructor-injection shape, not by embedding `*purchase.Service`.
