# MCN-401 Timeout → reversal and SAF — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans with superpowers:test-driven-development. Worktree `../mcn-worktrees/gw-401-saf`, branch `feat/MCN-401-saf`. Requires MCN-303 merged (`purchase.Service`, `store.TranLogRepository`, `internal/isonet.Supervisor`/`Mux`). Builds against the fake-issuer pattern already used by `purchase.Service`'s tests; the real Toxiproxy `kill -9` scenario (AC4) is an integration-checkpoint concern, covered by `make chaos` in MCN-407, not by this plan's unit/integration tests.

**Goal:** A purchase that times out (or is cancelled by the POS) never silently loses money: in one DB transaction the transaction moves `TIMED_OUT`/`SENT` → `REVERSAL_PENDING` and a 0420 is durably queued in `saf_queue`; a background worker delivers it (0420 then 0421 repeats, full-jitter backoff, `SKIP LOCKED`) until the issuer ACKs with 0430 or the item goes `DEAD` after `max_attempts`.

**Architecture:** `internal/saf` owns the queue and the worker. `SafRepository` (in `internal/store`, alongside `TranLogRepository`) does `Enqueue`, `ClaimDue` (`FOR UPDATE SKIP LOCKED`), `MarkAcked`, `MarkDead`, `Reschedule`. `purchase.Service.CreatePurchase`'s timeout branch (currently just sets `Transaction{Status: "TIMED_OUT"}`, per `service.go`'s `case errors.Is(err, context.DeadlineExceeded)`) is extended to call a small `ReversalQueuer` port that, inside the same `tranLog` transaction as the `TIMED_OUT`→`REVERSAL_PENDING` state write, builds the 0420 fields and calls `safRepo.Enqueue`. A new `internal/saf.Worker.Run(ctx)` polls `ClaimDue`, sends via the same `MuxSender` interface `purchase.Service` already uses, and reuses `isonet.Backoff{Base: 2*time.Second, Cap: 60*time.Second}` (already implemented for reconnect backoff — same full-jitter algorithm applies verbatim to advice repeats per `docs/03` §7.3/§9). `POST /v1/transactions/{rrn}/cancellations` (`internal/api/purchases.go`, new handler) reuses the same `ReversalQueuer.Queue` with reason `17` instead of `68`.

**Tech Stack:** Go 1.24, `pgx`, existing `internal/isonet`, `internal/store`, `internal/purchase`, `internal/journey`, chi.

**Spec:** `docs/03-iso8583-interface-spec.md` §7.3 (0420/0421/0430, DE 39 reasons `68`/`17`, DE 90 layout), §9 (timers: advice ack timeout 10s, backoff 2s base/60s cap), `docs/05-data-model.md` §2/§3 (`acquirer.saf_queue`), `docs/assets/baseline-schema.sql` lines 440-463 (`saf_queue` exact DDL, already transcribed below), `contracts/openapi.yaml` (`/v1/transactions/{rrn}/cancellations`, `SafItem`), `docs/06-user-stories.md` MCN-401.

## Global Constraints

- Money stays `int64` minor units; no new money fields here (a reversal carries no separate amount field on the wire beyond what DE 90 encodes; `saf_queue` stores the packed message, not amount).
- `tran_log.state` CHECK constraint (`migrations/00002_transactions.sql`) **already lists** `REVERSAL_PENDING` and `REVERSED` — no `ALTER TABLE` needed for the status enum, only the new `saf_queue` table.
- SAF payload (`payload_enc BYTEA`) is stored encrypted-at-rest per the baseline schema's own comment ("message mã hóa vì có thể chứa PAN") — for v1 use the same at-rest encryption helper other PAN-bearing columns use (`obs`/`store`'s existing AES-GCM helper if one exists; if none exists yet, this plan's Task 2 adds `store.EncryptBytes`/`DecryptBytes` backed by a `SAF_ENC_KEY` env var, validated at startup per `docs/10-engineering-standards.md` §11 — confirm no such helper already exists before writing a new one, per the ladder: reuse first).
- No PAN ever appears in a log line or the `SafItem` API response; `/v1/network/saf`'s `SafItem` schema has no PAN field at all — confirm this while implementing the (already-existing, MCN-204-adjacent) `GET /v1/network/saf` handler's DTO mapping.
- Every SAF advice repeat is a `0421`, never a second `0420`, per `docs/03` §7.3 semantics (`attempts > 0` ⇒ repeat bit / MTI `0421`) — mirrors the existing DDL comment in `baseline-schema.sql`.

## Ruling 1: `saf_queue` DDL — transcribe verbatim, don't redesign

`docs/assets/baseline-schema.sql` lines 440-463 already define `acquirer.saf_queue` completely, including the exact SKIP LOCKED query pattern as a comment. Transcribe it schema-prefix-stripped into a new migration, matching MCN-303's transcription convention. No column changes — the existing `attempts`/`max_attempts`/`next_retry_at`/`status` shape is exactly what full-jitter backoff and `SKIP LOCKED` claiming need.

## Ruling 2: SAF item ↔ original transaction correlation

`saf_queue.tran_id` (a real FK to `tran_log(id, business_date)`) is the join key MCN-402 (issuer side) never sees directly — the issuer only sees DE 90 on the wire. The gateway is the only side that needs `tran_id`; DE 90 is built from the *original* transaction's own MTI/STAN/DE7/acquirer-ID at enqueue time (read from the `tran_log` row being reversed, not recomputed). This Ruling is the one SPRINT-5.md's cross-story table calls out: MCN-402 must locate the original purely from DE 90's four components (original MTI, original STAN, original DE 7, original acquirer ID) — it never receives or needs `saf_queue.id` or `tran_log.id`, both purely internal to the gateway.

## Ruling 3: journey vocabulary for MCN-406

`internal/journey`'s `StepKind` today only has `KindOK`/`KindBad`/`KindWarn`/`KindInfo` (`journey.go`), but `contracts/openapi.yaml`'s `StepKind` enum also has `REVERSAL`, and its `Actor` enum also has `SAF`/`ACQUIRER`/`NETWORK`/`SWITCH` beyond the gateway's current `ActorPOS`/`ActorIssuer`. This plan adds `KindReversal StepKind = "REVERSAL"` and `ActorSAF Actor = "SAF"` to `journey.go`, and extends `buildStep`'s switch with cases for `"REVERSAL_PENDING"` (kind `WARN`, actor `POS`, easy text "Reversal queued") and `"REVERSED"` (kind `REVERSAL`, actor `SAF`, easy text "Money returned"). MCN-406 (WEB) consumes exactly these two new `Kind`/`Actor` string values — do not invent different ones.
