# MCN-506 PCI scanning in CI — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans with superpowers:test-driven-development. Worktree `../mcn-worktrees/plat-506`, branch `chore/MCN-506-pci-scan`. Requires MCN-005 merged (Sprint 0). Lane PLAT: `Makefile`, `scripts/pci-scan/`, `.github/workflows/ci.yml`.

**Goal:** `make pci-scan` scans E2E/chaos-run logs, fixtures (except the allow-listed `contracts/fixtures/cards.json` simulator fixture), and a DB dump for Luhn-valid PANs, PIN block patterns and track-2 patterns; CI fails the build on any finding; `gitleaks` runs for secrets.

**Architecture:** A standalone Go CLI (`scripts/pci-scan/main.go` — no dependency on `gateway-go`'s module, since PLAT owns this and it must run independent of any one service's build) walks a configurable set of input paths (log directories, a Postgres `pg_dump` output file, arbitrary fixture directories), applies three regex+checksum detectors (`internal Luhn-valid 13-19 digit run`, `ISO 9564-1 format-0 PIN block shape`, `ISO 7813 track-2 pattern`) line by line, and reports every match with file/line/detector, excluding any path matching an explicit allowlist (`contracts/fixtures/cards.json` only, per AC1's "except the allow-listed simulator fixture"). `gitleaks` (an already-widely-used, off-the-shelf secret scanner — reached for directly per the ladder's rung 5, no custom secret-detection code written) runs as a separate step in the same `make pci-scan` target and the same CI job.

**Tech Stack:** Go 1.24 (scanner CLI, stdlib `regexp` + a small Luhn checksum function — no new dependency), `gitleaks` (pinned version, downloaded in CI the same way other CI-only tools are — confirm the exact install pattern other CI steps already use, e.g. `golangci-lint`'s `go install` in `lint-test-gw`, and reuse gitleaks' own documented GitHub Action if that's simpler and matches the repo's existing "prefer off-the-shelf" bias).

**Spec:** `docs/06-user-stories.md` MCN-506-AC1/AC2, root `CLAUDE.md` §3 (`make pci-scan` already documented as a top-level command) and §6 rule 2 (PCI DSS: never log/persist/return PAN/track2/CVV/PIN/PIN-block/clear-keys), `Makefile:73-74` (current stub), `contracts/fixtures/cards.json` (the one allow-listed fixture — its own `_comment` field already states "They must never appear in API responses, logs or the browser," which is exactly the invariant this scanner enforces everywhere *except* this one intentional fixture file), `.github/workflows/ci.yml` (existing job/path-filter structure to extend, not replace).

## Global Constraints

- The scanner itself never writes a discovered PAN/PIN-block/track-2 value in full to its own output — findings report file/line/detector and a masked preview (first 6 + last 4, reusing the exact masking convention `docs/10-engineering-standards.md`/root `CLAUDE.md` §6 rule 2 already mandate), never the raw match.
- `contracts/fixtures/cards.json` is the **only** allow-listed path; a new fixture file with real-looking PANs anywhere else is a finding, not silently ignored — this is the point of the scanner.
- `make pci-scan`'s current `@echo "not implemented until MCN-506"; exit 2` stub (`Makefile:73-74`) is fully replaced.
- CI must fail (non-zero exit) on any finding from either the PAN/PIN-block/track scanner or `gitleaks` — a partial pass (one green, one red) still fails the job.

## Ruling 1: Luhn check, not just digit-length, to avoid drowning in false positives on RRNs/STANs/amounts

A bare `\b\d{13,19}\b` regex (the same pattern `gateway-go/internal/obs/mask.go`'s `MaskPAN` already uses for *masking*, confirmed by reading it) would flag plenty of non-PAN numbers in logs — amounts, timestamps concatenated, etc. — as false positives when used for *scanning* (a masking false-positive is harmless over-masking; a scanning false-positive is CI noise that trains people to ignore the gate). This plan's PAN detector requires both the length window (13-19 digits) **and** a passing Luhn checksum before it counts as a finding — this is a stricter bar than `MaskPAN`'s own regex (intentionally: `MaskPAN` prefers to over-mask, this scanner must not over-flag or the gate becomes noise nobody trusts, per the risk of "CI red time" root `CLAUDE.md`/`docs/07`'s retro metrics already track). `docs/06-user-stories.md` MCN-506-AC1's wording ("Luhn-valid PANs") confirms this is the intended bar, not an invented one.

## Ruling 2: track-2 and PIN-block detectors are pattern-only (no checksum equivalent), scoped narrowly

Track-2 (ISO 7813: `;PAN=YYMM...?`, or the unseparated `PAN=YYMM...` form) has no per-se checksum beyond the embedded PAN's own Luhn digit, so the track-2 detector requires the `;`/`=` structural markers plus an embedded Luhn-valid PAN segment — not just "18 digits with an equals sign," which would over-fire on unrelated key=value log lines. PIN block (ISO 9564-1 format 0: a fixed-length 16-hex-char string starting with `0` + a length nibble in `4`-`C`) has no checksum at all — the detector matches the structural shape only (`^0[4-9A-C][0-9A-F]{14}$` over 8-byte/16-hex-char runs) and accepts a higher false-positive rate here specifically, since PCI DSS rule 2's cost of a missed PIN block is categorically worse than an occasional noisy match a human dismisses in review.

```go
import (
	"os"
	"path/filepath"
	"testing"

	"github.com/stretchr/testify/require"
)

func TestWalk_skipsAllowlistedFixtureButFlagsOthers__MCN_506_AC1(t *testing.T) {
	dir := t.TempDir()
	require.NoError(t, os.MkdirAll(filepath.Join(dir, "contracts", "fixtures"), 0o755))
	require.NoError(t, os.WriteFile(filepath.Join(dir, "contracts", "fixtures", "cards.json"), []byte(`{"pan":"9704360000004417"}`), 0o600))
	require.NoError(t, os.WriteFile(filepath.Join(dir, "app.log"), []byte("card 4111111111111111 approved\n"), 0o600))

	findings, err := Walk([]string{dir}, []string{"contracts/fixtures/cards.json"})

	require.NoError(t, err)
	require.Len(t, findings, 1)
	require.Equal(t, "app.log", filepath.Base(findings[0].File))
}
```

Check: `9704360000004417` (the real fixture PAN from `contracts/fixtures/cards.json`) is itself Luhn-valid — this test deliberately uses the real fixture content so the allowlist is proven against the actual pattern it needs to exclude, not a synthetic stand-in.
