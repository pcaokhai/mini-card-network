# Sprint 8 — Execution Overview

> **For Claude:** This file orchestrates Sprint 8. Each story has its own plan (`MCN-601.md`, `MCN-701-ISS.md`/`MCN-701-GW.md`, `MCN-703.md`, `MCN-705.md`, `MCN-801.md`). Execute each plan with superpowers:subagent-driven-development (or superpowers:executing-plans), one worktree per story, following root `CLAUDE.md` §4.

**Sprint goal:** Holds and events flowing to settlement. `MCN-601` finishes **Slice S6** (real issuer-side pre-authorization/completion, on top of Sprint 7's MCN-602/603/604 groundwork). `MCN-701` (both lanes) stands up the first real outbox-to-Kafka relays, feeding `MCN-703`'s settlement ingestion — the first real code in `settlement/`. `MCN-801` lays switch/BIN-routing groundwork for Sprint 9's stand-in processing. `MCN-705` builds the settlement screen MSW-mocks-first, ahead of its slice-mates `MCN-702`/`MCN-704` (Sprint 9). **Duration:** 2 weeks. **Commitment:** 5 (MCN-601) + 3 (MCN-701, split ISS+GW) + 5 (MCN-703) + 5 (MCN-705) + 5 (MCN-801) = 23 points. **Release:** R6, per `docs/07-delivery-plan.md` §2/§3 (Slice S6 = MCN-601+MCN-603 backend / MCN-604 frontend, flag `FF_S6_ADV_TXN`, completed by `MCN-601` this sprint).

**Contract-first check:** No `contracts/` PR is needed this sprint. `docs/07-delivery-plan.md`'s Sprint 8 row lists no new slice contract, and direct inspection confirms why: the settlement REST paths (`contracts/openapi.yaml:429-484`, `SettlementDay`/`ReconBreak`/`ClearingFile` schemas) were already scaffolded ahead of need in an earlier sprint (the same "scaffolded ahead of need" pattern `SPRINT-6.md`/`SPRINT-7.md` documented for `KeyInfo`/`KeyRotation`), the Kafka event schema (`contracts/events/transaction-event.schema.json`) already exists and needed no changes for `MCN-701`/`MCN-703`'s use of it, and the switch/network path (`docs/02-software-architecture.md`'s topology, `MCN-801`) introduces a new *service*, not a new *contract* — the gateway's REST/WS surface toward `web-next` is unchanged, only an internal TCP hop is added between the gateway and the issuer.

## Rulings for the whole sprint

| Ruling | Why | Cost if wrong |
| --- | --- | --- |
| Kafka topic names (`issuer.transactions.v1`, `acquirer.transactions.v1`) and the partitioning key (RRN, via `kafka.Hash{}`/Java's default hash partitioner) are fixed once in `MCN-701-ISS.md`'s Ruling 1 and restated verbatim in `MCN-701-GW.md`'s Ruling 1 — both derived directly from `contracts/events/transaction-event.schema.json`'s own `title` field, not independently invented per lane | `MCN-703.md`'s Kafka consumers (`IssuerTransactionConsumer`/`AcquirerTransactionConsumer`) subscribe to these exact topic names; a per-RRN partition-ordering guarantee (needed for `MCN-703`'s eventual reconciliation-time original/reversal matching) only holds if both publishers key on RRN identically | A topic-name or partition-key mismatch between the two `MCN-701` lanes would either leave `MCN-703` subscribed to a topic nothing publishes to (silent, caught only when no events ever arrive — an obvious, fast-failing signal) or break per-RRN ordering silently (a subtler bug, only visible once `MCN-704`'s reconciliation logic, Sprint 9, starts comparing out-of-order events) |
| The exact shape of `contracts/events/transaction-event.schema.json` (`eventId`/`eventType`/`source`/`occurredAt`/`businessDate`/`rrn`/`stan`/`transmissionDateTime`/`acquirerId`/`terminalId`/`transactionType`/`amount`/`currency`/`status`/`responseCode`/`authCode`/`originalRrn`/`maskedPan`, `additionalProperties: false`) is the one all three of `MCN-701-ISS`, `MCN-701-GW`, and `MCN-703` map to/from — read directly from the already-existing schema file by all three plans, none inventing its own variant | `additionalProperties: false` means a publisher adding an undocumented field would fail schema validation (if enforced) or silently be dropped by a strict consumer deserializer; `MCN-703`'s `TransactionEventDto` Jackson mapping must accept exactly this field set | A field-name mismatch (e.g. one lane emitting `terminal_id` instead of `terminalId`) would fail JSON deserialization at `MCN-703`'s consumer, caught immediately by `IngestionIntegrationTest` rather than silently — still worth flagging here since three independently-executed plans increase the chance of a typo drifting from the schema |
| `MCN-701`'s at-least-once delivery (a relay crash between Kafka ack and `markPublished`/`MarkPublished` can republish a row) is accepted, not eliminated, in both `MCN-701-ISS.md`'s and `MCN-701-GW.md`'s Ruling 2 — `MCN-703.md`'s inbox pattern (dedup on `event-id`, `settlement.inbox_event`) is the sprint's actual answer to that gap, not a second fix built into either relay | Building exactly-once delivery (transactional outbox-to-Kafka CDC) into either relay would duplicate what the inbox pattern already solves at the consumer, and adds infrastructure (Debezium/Kafka Connect) this project has no other use for | If `MCN-703`'s inbox dedup were ever silently dropped or weakened in a future change, every relay's accepted at-least-once behavior would start producing real duplicate `clearing_record` rows — this Ruling exists so a future editor of `MCN-703`'s code understands the inbox table is load-bearing, not incidental |
| `MCN-705`'s scope this sprint is the wizard shell and MSW-driven states only (`MCN-705.md`'s Ruling 1) — `MCN-702`/`MCN-704`'s real cutover/reconciliation/clearing-file logic is Sprint 9, and this sprint's integration checkpoint does not include a real-backend settlement journey | `docs/07-delivery-plan.md`'s Slice S7 pairs `MCN-702`/`MCN-704` with `MCN-705` on release R7 (Sprint 9), but the wave table pulls only `MCN-705` into Sprint 8 — claiming a real end-to-end settlement journey works this sprint would be dishonest about what's actually been proven, the same "pulled forward, honestly scoped" precedent `MCN-603.md`'s Ruling 1 set in Sprint 7 | A tech-lead review assuming `MCN-705` proves real cutover/reconciliation would be surprised at the Sprint 9 integration checkpoint when `MCN-702`/`MCN-704` reveal gaps a false "done" signal from Sprint 8 papered over |
| `MCN-801`'s BIN routing table is a static startup-loaded config (`MCN-801.md`'s Ruling 1), not a database-backed hot-reloadable table, and its two pooled issuer connections both point at the same single lab issuer (Ruling 2) — a BIN-to-issuer-exclusive routing scheme is explicitly not built this sprint since this project has only one issuer | Building a database-backed routing table or a multi-issuer routing scheme for a lab project with one issuer and one BIN range would be pure speculative generality (YAGNI) — `MCN-802` (Sprint 9, stand-in processing) is the story that would need multi-issuer or dynamic routing if it ever does | If `MCN-802` turns out to need dynamic BIN routing, that story's own plan adds it then — not retrofitted speculatively into `MCN-801` now |
