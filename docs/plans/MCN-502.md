# MCN-502 PIN translation and MAC (gateway) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans with superpowers:test-driven-development. Worktree `../mcn-worktrees/gw-502`, branch `feat/MCN-502-pin-mac`. Requires MCN-501 (both `MCN-501-ISS.md` and `MCN-501-GW.md`) merged — this plan extends `internal/hsm.Module` (the port) and `hsm.JCEModule` (the implementation) rather than creating a new package. **Task 1 is a `contracts/` PR and must merge before Task 2 starts** — per root `CLAUDE.md` §9, contract changes never land inside a feature branch that also changes service code.

**Goal:** The gateway translates an incoming PIN block from TPK to ZPK (DE 52) and MACs the full packed 0200 request under ZAK (DE 64/128) before sending it to the issuer; validates the MAC on every incoming 0210; a bad incoming MAC fails the transaction with RC `96`, queues a reversal (reusing MCN-401's `ReversalQueuer`), and increments `mcn_mac_failure_total`.

**Architecture:** `internal/hsm.Module` (from MCN-501) gains two methods: `TranslatePIN(pinBlockUnderTPK []byte, tpk, zpk []byte) ([]byte, error)` (decrypt under TPK, re-encrypt under ZPK — a real HSM never exposes the clear PIN block outside this one call; `JCEModule`'s implementation decrypts and re-encrypts inside one function body, never returning the intermediate clear value) and `ComputeMAC(packedMessage []byte, zak []byte) ([]byte, error)` (ISO 9797-1 algorithm 3 / Retail MAC / X9.19, per `docs/03` §11, returning the last 8 bytes). `purchase.Service.sendPurchase` (MCN-303/401/404, already extended twice) gains a MAC step: after `codec.Pack` produces the outgoing bytes, `hsm.ComputeMAC` runs over the packed message excluding the MAC field itself, and the result is placed in DE 64 (or DE 128 when a secondary bitmap is present — `internal/iso8583`'s existing bitmap logic already decides which). On receipt of a 0210, the same computation runs over the received packed bytes (excluding DE 64/128) and is compared to the response's own DE 64/128; a mismatch sets RC `96`, calls the existing `saf.ReversalQueuer.Queue(ctx, txn, "06")` (reason `06` = error, per `docs/03` §7.3's DE 39 table — reused exactly as MCN-401 defined it, no new reason code invented), and increments `obs.MacFailureTotal`.

**Tech Stack:** Go 1.24, `crypto/des` (Retail MAC / ISO 9797-1 alg 3 is a DES/3DES-based MAC per the ISO 8583 security convention — confirmed against `docs/03` §11's own naming, "X9.19"), existing `internal/hsm`, `internal/purchase`, `internal/saf`.

**Spec:** `docs/06-user-stories.md` MCN-502-AC1/AC2/AC3, `docs/03-iso8583-interface-spec.md` §11 ("MAC: ISO 9797-1 algorithm 3 (Retail MAC, X9.19) over the full packed message excluding the MAC field, using ZAK; last 8 bytes placed in DE 64 (or DE 128 when secondary bitmap present). A MAC failure is answered with RC 96 and counted in mcn_mac_failure_total." and "PIN block: ISO 9564-1 format 0 ... Encrypted under TPK at the POS, translated to ZPK by the gateway, verified via PVV by the issuer."), `gateway-go/internal/iso8583/spec_gen.go:28,32,44` (DE 52/64/128 are type `b`, length 8 — binary, fixed 8 bytes), MCN-501-GW.md (the `hsm.Module` port and `KeyStoreRepository` this plan extends), MCN-401's `saf.ReversalQueuer` (`internal/saf/reversal.go`, `Queue(ctx, txn, reasonCode) error`).

## Global Constraints

- The clear PIN block is never logged, stored, or returned by any API — it exists only inside `hsm.TranslatePIN`'s function body, as `[]byte`, for the duration of one decrypt-then-reencrypt call.
- DE 64/128 carry only the 8-byte MAC — never the ZAK, never intermediate MAC state.
- Money and all other Global Constraints from root `CLAUDE.md` §6 remain unchanged; this story adds no new money field.
- `mcn_mac_failure_total` is a `prometheus.Counter`, matching `internal/obs/metrics.go`'s existing counters (`LateResponseTotal`, `SafDeadTotal`) exactly in shape and registration style.

## Ruling 1: Task 1 is a contract-only PR, kept minimal — MAC vectors, nothing else

`contracts/iso8583/vectors/` currently has `0200-purchase-chip-pin.json`, `0210-approved.json`, `0420-reversal-timeout.json`, `0800-echo.json` (confirmed by listing the directory) but no `mac/` subdirectory. This plan's Task 1 adds `contracts/iso8583/vectors/mac/0200-with-mac.json` and `contracts/iso8583/vectors/mac/0210-with-mac.json` — each a fixed request/response pair with a known ZAK test value and the expected 8-byte MAC (computed once by running the reference algorithm, same as any golden vector) — as a **separate PR that touches only `contracts/`**, merged before Task 2's service code starts, per root `CLAUDE.md` §9's "do not change contracts/ inside a feature branch that also changes a service" and `docs/03` §12 ("Adding a field or message type starts with a vector"). `make contracts` (golden vectors, both codecs) must pass against these new vectors once Task 2's `hsm.ComputeMAC` exists — Task 2's own tests reference the same vector files so a MAC algorithm bug shows up as a vector mismatch, not just a passing unit test with an invented expected value.

## Ruling 2: ZAK/MAC field format — the contract both MCN-502 and MCN-503 build against

Both this plan (gateway, producing/verifying the MAC on the acquirer side) and `MCN-503.md` (issuer, verifying the MAC on the issuer side) compute the *same* Retail MAC algorithm over the *same* packed bytes, using their own respective ZAK copies (both sides hold the same ZAK value out of band in v1 — no dynamic key exchange yet, that's MCN-504/Sprint 7). This Ruling fixes, for both stories: **MAC input** = the full ISO 8583 packed message (MTI + bitmap(s) + all present fields in field-number order) with DE 64 (or DE 128) *excluded* from the byte sequence being MAC'd (not zeroed — genuinely absent, since the sender computes the MAC before appending DE 64/128 to the message); **MAC output** = 8 bytes, placed verbatim in DE 64 when no DE 65-127 is present, DE 128 when a secondary bitmap exists (mirrors the existing DE 64/128 selection logic `internal/iso8583` already has for other conditionally-present fields — reuse it, confirmed present in Task 2). Both stories reference the same `contracts/iso8583/vectors/mac/*.json` fixtures from Task 1, so a format drift between the two lanes shows up as one side failing the golden vectors, not as a silent runtime mismatch discovered only at integration.
